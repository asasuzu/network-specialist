SNMP・ping 監視・syslog などの監視と、運用の自動化。

## 時刻同期

### Gメーターを長時間動かすと、時刻の誤差で、どんな問題が起きる？
- 段階: 過去問
- 出典: R7 午後Ⅱ 問2 設問4(5)
- 本文: ◎
- 状況: Y社のGメーターは、1時間ごとに測定して測定時刻と測定値を記録し、毎日午前0時の測定のあとに送信する。時刻は、Gメーター内のリアルタイムクロックで管理する。精度の高いクロックを載せても、長時間動かすと、時刻の誤差が無視できないほど大きくなるおそれがある。

**測定と送信が誤った時刻に行われることになる。**

Gメーターは、**自分の時計** を見て、「毎時ちょうどに測定する」「午前0時の測定のあとに送信する」と動く。時計がずれると、測定のタイミングも送信のタイミングも **ずれた時刻** で行われ、**測定時刻の記録もずれる**。管理サーバは、全てのGメーターのデータを受け取ったあとに集計するので、ずれたデータが混ざると集計にも影響する。

時計は、どんなに精度が高くても、**長く動かすと少しずつずれる**（ずれが積み重なる）。だから、定期的に **正しい時刻に合わせ直す** 仕組みが必要になる。

### Gメーターの時刻の誤差を抑えるために、CoAP通信でどんな処理を組み込む？
- 段階: 過去問
- 出典: R7 午後Ⅱ 問2 設問4(6)
- 本文: ○
- 状況: Y社のGメーター（CoAPクライアント）は、Gメーター管理サーバ（CoAPサーバ）とCoAPで通信する。Y社サービス拠点のサーバは、NTPサーバと時刻同期をしている。Gメーターの時刻の誤差を抑えるため、CoAP通信を使った処理を組み込む。

**Gメーター管理サーバから現在時刻を取得して、Gメーターの時刻を更新する。**

Gメーター管理サーバは、Y社サービス拠点で **NTPサーバと時刻同期** しているので、正確な時刻を持っている。Gメーターは、CoAPで **GETメソッド** などを使って管理サーバの現在時刻をもらい、自分の時計を **その時刻に合わせ直す**（たとえば、毎日のデータ送信のついでに行う）。

> 「機器の時計がずれる問題」→ **正確な時刻を持つサーバから定期的に時刻をもらって補正**（NTPと同じ考え方）。

## NetFlow

### NetFlow とは？ 何のために使う？
- 段階: 知識
- 出典: R6 午後Ⅰ 問1

**ルータなどを通過した通信を「フロー」（送信元・宛先のIPアドレス、ポート番号、プロトコル、バイト数など）の単位で集計して、分析用のサーバへ送る仕組み。** NetFlow v9 は RFC 3954 で定義されている。

- SNMPでは「どの回線がどれだけ使われているか」までしか分からないが、NetFlow なら **誰から誰へ、何の通信が、どれだけ流れているか** まで分かる
- 使い道：トラフィックの分析、異常（攻撃）の検知
- 類似の規格：IPFIX（標準化版）、sFlow（サンプリング方式）

R6 午後Ⅰ 問1：E社のBGPルータが、インターネット側から入ってくるパケットのNetFlowを作ってDDoS検知サーバへ送り、サーバが攻撃の有無を判断する。

## 死活監視

### ping監視・TCP接続監視・URL接続監視は、それぞれ何を確認する？
- 段階: 知識
- 出典: R4 午後Ⅱ 問2

| 監視 | やること | 正常のしるし | わかること |
|---|---|---|---|
| **ping監視** | **ICMPエコー要求** を送る | **ICMPエコー応答** が返る | IPパケットが **届くか**（機器が生きているか、L3） |
| **TCP接続監視** | **SYN** を送る | **SYN/ACK** が返る | そのポートが **待ち受けていて**、TCPで通信できるか（L4） |
| **URL接続監視** | HTTPの **GET** メソッドで、リソースを要求する | 一定時間内にリソースが取得できる | **HTTPサーバ（AP）が正常に動いているか**（L7） |

下の段ほど「アプリに近い」確認。複数を組み合わせると、**どの層で壊れているか** を推測できる。

- ping○ → TCP× → URL×：機器は生きているが、**アプリ（ポート）が止まっている**
- ping× → TCP× → URL×：**機器そのもの** が止まっている（通信できない）

### 死活監視（ping監視）はどんな仕組み？ 何ができて、何ができない？
- 段階: 知識
- 出典: R3 午後Ⅱ 問2 設問4(1)

**死活監視** ＝ 監視サーバが監視対象に **ICMPエコー要求（ping）を送って、エコー応答が返るか** で、機器が生きているかを確かめる。

R3 午後Ⅱ 問2 の例：1回につき3パケット、1分おきに、タイムアウト1秒。**5回連続で1つも応答がなければアラート**。

- **できる**：機器の停止、リンクの断絶など、**完全につながらない** 状態の検知
- **できない**：**輻輳**（混んでいて遅い）の検知。混んでいても、3パケットのうち数個は応答が返ってくるので、「死んでいる」とは判定されない
- 応答がないとき、原因が **機器の故障なのか、途中の回線の障害なのか** は、pingだけでは区別できない

### ping監視では不十分なのはなぜ？
- 段階: 過去問
- 出典: R5 午後Ⅱ 問1 設問1(2)
- 本文: ◎
- 状況: A社では、監視サーバがICMPのping監視でDMZやIaaSのサーバを監視している。プロキシサーバの監視を強化するため、プロキシのアプリケーションが動作するポート番号にTCP接続できるかを調べるTCP監視を追加することにした。

**プロキシサーバのアプリケーションプロセスが停止した場合に検知できないから**

pingはOS（ネットワーク層）が応答するかを見るだけ。プロキシのプロセスだけが止まっても、OSは生きているのでpingには応答してしまう。TCP監視ならそのポートへ接続できなくなるので検知できる。

> 「〇〇監視では不十分な理由」→「**その監視では確認できない層（アプリの動作）の障害を見逃すから**」。

### 監視サーバが正常と判断する条件は？ ping監視でICMPの何を受信すること？ TCP接続監視で何を受信すること？ URL接続監視でHTTPのどのメソッドで取得できること？
- 段階: 過去問
- 出典: R4 午後Ⅱ 問2 設問4(1)
- 本文: ◎

- ping監視（ICMPで受信するもの）：**エコー応答**（ICMPエコー要求への返事）
- TCP接続監視（受信するもの）：**SYN/ACK**（SYNへの返事。TCP接続の確認）
- URL接続監視（HTTPのメソッド）：**GET**（リソースを取得する）

詳しい違いは「ping監視・TCP接続監視・URL接続監視は、それぞれ何を確認する？」を参照。

### ping、TCP接続、URL接続の監視のうち、項番2・4・7で障害を検知し、それ以外は正常。どこに障害がある？
- 段階: 過去問
- 出典: R4 午後Ⅱ 問2 設問4(2)
- 本文: △
- 状況: U社の監視サーバは、表5のとおり、8項目を監視している。ping監視：共用リバースプロキシ（項番1）、コンテナサーバa（2）、コンテナサーバb（3）。TCP接続監視：WebAPコンテナ（AP0a）192.168.0.112:8000（4）、WebAPコンテナ（AP0b）192.168.0.113:8000（5）。URL接続監視：共用リバースプロキシ経由で ap0.u-sha.com（6）、WebAPコンテナ（AP0a）（7）、WebAPコンテナ（AP0b）（8）。

**コンテナサーバa**。

項番ごとの結果：

| 項番 | 監視 | 結果 | 意味 |
|---|---|---|---|
| 1 | ping 共用リバースプロキシ | 正常 | プロキシは生きている |
| **2** | **ping コンテナサーバa** | **異常** | **コンテナサーバaに届かない** |
| 3 | ping コンテナサーバb | 正常 | b は生きている |
| **4** | **TCP AP0a** | **異常** | aにつながらない |
| 5 | TCP AP0b | 正常 | AP0bは生きている |
| 6 | URL 共用リバースプロキシ経由 | 正常 | AP0bが応答している |

| 8 | URL AP0b | 正常 | |

ping（IPの到達性）が失敗しているので、**TCPやHTTPの失敗は、そのせいで起きたもの**。コンテナサーバaそのもの（電源、OS、NIC、回線など）が止まっている。項番6が正常なのは、振り分け先から異常なAP0aが外れ、AP0bだけで答えているから。

> 監視の結果から障害箇所を推測 →「**下の層（ping）から見る**」。pingが失敗していれば、それより上は全部その結果。

### 項番4・7で障害を検知し、それ以外は正常。どこに障害がある？
- 段階: 過去問
- 出典: R4 午後Ⅱ 問2 設問4(3)
- 本文: △
- 状況: U社の監視サーバは、ping監視、TCP接続監視、URL接続監視を組み合わせて、8項目を監視している。今回は、WebAPコンテナ（AP0a）の TCP 接続監視（項番4、192.168.0.112:8000）とURL接続監視（項番7）だけが異常で、コンテナサーバaへのping監視（項番2）を含む、それ以外は全て正常だった。

**WebAPコンテナ（AP0a）**。

- コンテナサーバa（ping）は **正常** → 物理サーバ・ネットワークは生きている
- AP0aの **TCP/8000** と **URL** が異常 → そのポートで待ち受けているのは、仮想ルータがフォワードする先の **WebAPコンテナ（AP0a）**。コンテナが停止している、アプリが止まっている

> 「ping○、TCP×」→ **機器は生きているが、そのポートで待っているアプリ（コンテナ）が死んでいる**。

### 専用線の輻輳を検知するため、ルータ10Zとルータ11Zを死活監視の対象に追加するときの問題点を二つ答えよ
- 段階: 過去問
- 出典: R3 午後Ⅱ 問2 設問4(1)
- 本文: ○
- 状況: A社の監視サーバは、死活監視として、1回につきICMPエコー要求を3パケット送り、1分おきに連続して5回、1つもエコー応答がなければアラートとして検知する（タイムアウト1秒）。Cさんは、専用線の輻輳を検知するため、ルータ10Z・ルータ11Z（Z社のルータ）を監視対象に追加することを考えたが、問題があるため見送った。

次の2つ（30字以内で、それぞれ）。
- **輻輳時にエコー応答を受信することがあり検知できない。**
- **ルータ10Zとルータ11Zの障害時に誤って検知する。**

1つめ：混んでいても、15パケット（3×5回）のうち1つでも応答が返れば、アラートにならない。輻輳では全部が落ちるとは限らない。
2つめ：応答がなくなる原因が、**専用線の輻輳ではなく、ルータ10Z・11Z自身の障害** でも同じ。区別できず、輻輳と誤って検知する。

> 「pingでXXを検知する問題点」→ **ping（ICMP）は、つながるか・つながらないかしか見ない**。混み具合（輻輳）は見えず、原因の切り分けもできない。

## パケットの取得

### 通信をコピーして監視する仕組み（ポートミラーリング、ネットワークタップ、NPB）とは？
- 段階: 基礎
- 出典: R4 午後Ⅰ 問1

| | ポートミラーリング | ネットワークタップ |
|---|---|---|
| 何をするか | L2SWの機能。指定したポートの送受信を、別のポートにコピーして出す | 既存の配線の途中に **インラインで挿入** する専用装置。通信をコピーして出す |
| 追加の機器 | 不要（スイッチの設定だけ） | タップ装置が必要 |
| コピーの出し方 | 送信側と受信側を **1本のミラー先ポートにまとめて** 出す | 送信側・受信側を **別々のポート** に出す（取得側に2ポート必要） |

**NPB**（ネットワークパケットブローカ）＝ コピーしたパケットを受け取り、**入力ポートと出力ポートの組合せを事前に決めて**、複数の出力ポートへさらに複製・フィルタリングして配る装置。

R4 午後Ⅰ 問1 では、制御セグメントのL2SWのミラーポート → NPB → 可視化サーバ（統計処理・グラフ化）とキャプチャサーバ（そのまま長期保存）、という流れ。

### L2SWのミラーポートからNPBにデータを入力する方式は、ネットワークタップを使う方式と比べて、性能面でどんな制約がある？（40字以内）
- 段階: 過去問
- 出典: R4 午後Ⅰ 問1 設問3(2)
- 本文: ○
- 状況: A社は、NPBへの入力を、L2SWのミラーポートから行うか、ネットワークタップから行うか検討した。NPBにつなぐケーブルは全て1000BASE-SX（1Gbps）。ネットワークタップは送信側・受信側それぞれの配線でパケットを複製するので、NPBの入力ポートが2ポート必要になる。

**送信側と受信側のトラフィックを、合計1Gbpsまでしか取り込めない。**

- ミラーポート方式：送信側と受信側のコピーを **1本のポートにまとめて** NPBに送る → そのポートの帯域（1000BASE-SX ＝ 1Gbps）が上限
- ネットワークタップ方式：送信側と受信側を別々のポートで受ける → **それぞれ最大1Gbps**

A社は想定トラフィックが少ないので、追加機器が要らないミラーポートを選んだ。

> 「ミラーポートの制約」→ **出力ポート1本の帯域に、送信側＋受信側の合計が収まる必要がある**。

### 制御セグメントのL2SWで、ミラーポート設定の取得元を1ポートだけにするなら、どの装置が接続されたポートにする？
- 段階: 過去問
- 出典: R4 午後Ⅰ 問1 設問3(3)
- 本文: △
- 状況: A社の工場の制御セグメントには、センサや工作機械につながる複数のコントローラ、制御サーバ、NPBが、L2SWにつながっている。コントローラは測定データを常時、制御サーバに送り続ける。L2SWの特定の1ポートの送受信をミラーして、NPBに送りたい。

**制御サーバ**（が接続されているポート）

図のつながり方（要点）：
- 制御セグメントのL2SWには、コントローラ（複数）、制御サーバ、NPBがつながる
- 測定データは、すべてのコントローラから **制御サーバへ** 集まる

コントローラ側のポートはたくさんあるが、**制御サーバのポートなら、全コントローラの通信（送信側も受信側も）が1ポートを通る**。だから1ポートの設定で全部取れる。

> 「1ポートでミラーするなら」→ **通信が必ず集まるポート**（サーバやルータに向かうポート）を選ぶ。

### サーバがミラーパケットを受信するには、インタフェースを何というモードにする？ また、そのモードで設定しない場合に比べて、どんなフレームを受信できるようになる？（30字以内）
- 段階: 過去問
- 出典: R4 午後Ⅰ 問1 設問3(4)
- 本文: ◎
- 状況: A社の可視化サーバとキャプチャサーバは、NPBが複製したミラーパケット（コントローラと制御サーバの間の通信のコピー）を受信する。

- モード：**プロミスキャス**（モード）
- 受信できるようになるフレーム：**宛先MACアドレスが自分のMACアドレス以外のフレーム**

ミラーパケットの宛先MACアドレスは、元の通信の相手（コントローラや制御サーバ）のもので、可視化サーバやキャプチャサーバのものではない。ふつうのNICは自分宛（とブロードキャスト・マルチキャスト）以外は捨てるが、プロミスキャスモードでは **宛先を問わず全部受け取る**。

> 「他人宛の通信を受け取るには」→ **プロミスキャスモード**（キャプチャ・IDSなどの監視機器の基本設定）。

### 100kビット/秒のミラーパケットを1,000日間保存するのに必要なディスク容量は？（1kビット＝10³ビット、1Gバイト＝10⁹バイト）
- 段階: 過去問
- 出典: R4 午後Ⅰ 問1 設問3(5)
- 本文: ◎
- 状況: A社のキャプチャサーバに流れるミラーパケットは平均100kビット/秒。これを圧縮せずに1,000日間保存する。メタデータの大きさは無視する。

**1,080 Gバイト**

1. 1日の秒数：24 × 60 × 60 ＝ **86,400秒**
2. 1,000日の秒数：86,400 × 1,000 ＝ 8.64 × 10⁷ 秒
3. ビット数：100 × 10³ × 8.64 × 10⁷ ＝ 8.64 × 10¹² ビット
4. バイト数：8.64 × 10¹² ÷ 8 ＝ 1.08 × 10¹² バイト ＝ **1,080 × 10⁹ バイト**

> 容量の計算 →「**ビット/秒 × 秒数 ÷ 8 ＝ バイト**」。単位（k、G、ビットかバイトか）を最後に揃える。

## syslog

### 機器から別のサーバへログを転送する標準規格（RFC 5424）のプロトコルは？
- 段階: 過去問
- 出典: R4 午後Ⅰ 問1 設問1(1)a
- 本文: ◎
- 状況: A社の工場では、制御サーバや操作端末が記録したアクセスログを、データヒストリアン（測定データやログを溜めておく装置）に転送している。このログ転送には、イベント通知を転送する標準規格（RFC 5424）のプロトコルが使われている。

**Syslog**

機器のログ（イベント通知）を、ネットワーク越しに **ログサーバへ集めて送る** プロトコル。ポートは **UDP/514**（「ポート番号」のカード参照）。

複数の機器のログを1台に集めると、あとで時系列に並べて調べられる。そのため機器の時刻はNTPで合わせておく。

> 「イベント通知／ログを転送する標準」→ **Syslog**。

## 移行

### DNS切替えで移行するときの手順は？ なぜこの順番？
- 段階: 基礎
- 出典: R4 午後Ⅱ 問2 表6

R4 午後Ⅱ 問2 表6（APサーバ → WebAPコンテナ）を一般化すると：

1. **新環境の構築**（コンテナ、設定）
2. **監視の登録**（新しい環境を監視対象に）
3. **動作確認**（テスト用PCだけで。hostsファイルなどで、DNSを変えずに新環境に向ける）
4. **DNS切替え**（DNSレコードを書き換えて、新環境へ向ける）
5. **旧環境の監視の削除**
6. **旧環境の停止**（旧環境にアクセスがなくなったことを確認してから）

旧環境と新環境を **並行稼働** させておくので、切替え中にどちらにアクセスが行っても同じ動作になり、問題が出ない。いつでも切り戻せるように、旧環境はすぐには止めない。

### システムを更改するとき、移行はどんな順番で進める？
- 段階: 基礎
- 出典: R3 午後Ⅱ 問1 表4

R3 午後Ⅱ 問1 の5ステップを一般化するとこうなる。

1. **共存環境を作る**：新システムを構築し、現行システムと接続する（1か月）
2. **データ移行と動作確認**：データを新しいサーバに移し、現行側のPCから新サーバの動作を確かめる（1か月）
3. **切り替え**：現行から新システムへ、短時間で切り替える（1日）

## SNMP・LLDP

### SNMPとは？ MIBのカウンタ値から通信量はどう求める？
- 段階: 基礎
- 出典: R3 午後Ⅱ 問2 設問1

**SNMP** ＝ ネットワーク機器の状態や統計を、**管理サーバ（マネージャ）が機器（エージェント）から集める** プロトコル。

- 集める情報の項目を **MIB** という（例：インタフェースの受信オクテット数 ifInOctets）
- 管理サーバは、一定間隔（R3 午後Ⅱ 問2 では5分ごと）で機器に問い合わせる（ポーリング、UDP/161）
- 機器側から異常を知らせる通知は **トラップ**（UDP/162）

通信量のMIB（ifInOctets など）は **カウンタ値**：機器の起動後、**受信したオクテット数（1オクテット＝8ビット）をどんどん足し算していった累計**。そこで通信量は、

**(今回のカウンタ値 − 前回のカウンタ値) ÷ 取得間隔（秒）** で求まる（ビットにするなら × 8）。

### LLDPとは？ 何がわかる？
- 段階: 知識

**隣にいる機器に、自分の情報を教える** プロトコル（IEEE 802.1AB）。OSI基本参照モデルの **第2層（データリンク層）** のプロトコル。

- 各機器が、**機器名・ポート名（IF名）・管理用IPアドレスなど** を、LLDPフレームで定期的に隣の機器に送る
- 受け取った機器は、隣の機器の情報を **LLDP-MIB** に覚えておく
- これを **SNMPで集めれば、「どの機器のどのポートが、どの機器のどのポートにつながっているか」** という接続の一覧を自動で作れる
- LLDPは **隣の機器にしか届かない**（スイッチは中継しない）。だから、間に別のLLDP対応機器をはさむと、その機器が隣になる
- **LLDP-MED**：LLDPをIP電話機などの端末向けに拡張したもの（VoIP用VLANやPoEの情報をやり取りする）

### SNMPのカウンタが「32ビット」と「64ビット」で、何が違う？ カウンタラップとは？
- 段階: 知識
- 出典: R3 午後Ⅱ 問2 表1・設問1(3)

| MIB | カウンタ | 上限 |
|---|---|---|
| ifInOctets・ifOutOctets | 32ビット | 2³² − 1 ＝ 約43億 |
| ifHCInOctets・ifHCOutOctets（HC＝High Capacity） | 64ビット | 事実上、ラップしない |

**カウンタラップ** ＝ カウンタが上限を超えて、**0に戻ってまた数え始める** こと。

32ビット（約43億オクテット ＝ 約344億ビット）は、**1Gbpsなら約34秒でラップする**。5分間隔のポーリングでは、1回だけでなく何回もラップして、通信量が正しく計算できない。だから、通信量が多い回線では **64ビットカウンタ（ifHC…）を使う**。

ラップが1回だけなら、**今回の値に 2³² を足して補正** して差を取れる（次のカードの例）。

### SNMPで5分ごとに取得したオクテット数のカウンタ値から、単位時間あたりの通信量（ビット／秒）を求める式は？
- 段階: 過去問
- 出典: R3 午後Ⅱ 問2 設問1(1)
- 本文: ◎
- 状況: A社の管理サーバは、SNMPで5分ごとにインタフェースの受信オクテット数（ifInOctets、カウンタ値）を取得している。時刻tの値をXt、5分前の時刻t−1の値をXt−1とする。1オクテットは8ビットで、t−1とtの間にカウンタラップは起きていないものとする。

**(Xt − Xt−1) × 8 ÷ 300**（ビット／秒）。

- 差 Xt − Xt−1 ＝ 5分間に増えたオクテット数
- × 8 ＝ ビットに換算
- ÷ 300 ＝ 5分（300秒）で割って、1秒あたりに

32ビットカウンタは、通信量が多いとすぐにラップする（1Gbpsなら約34秒）ので、通信量が多い回線では64ビットカウンタ（ifHCInOctets）を使うことが推奨されている。

> 計算問題 → **「差 × 8 ÷ 秒数」**。取得間隔が5分なら300、1分なら60。

### 取得したカウンタ値から求めた通信量（ビット／秒）を、5分間の平均にすると、どんな問題がある？
- 段階: 過去問
- 出典: R3 午後Ⅱ 問2 設問1(2)
- 本文: ◎
- 状況: A社の管理サーバは、5分ごとにSNMPでカウンタ値を取得して、その差から単位時間あたりの通信量（ビット／秒）を計算し、統計データとして保存している。専用線で、過去に何度か利用が増えて輻輳が起きていたことがわかった。

**取得間隔の間で発生したバースト通信が分からなくなる。**（35字以内）

カウンタ値の差を取ると、**5分間の平均** しかわからない。たとえば最初の10秒間だけ帯域を使い切っても、残りの4分50秒が静かなら、平均は低い値に埋もれる。短い時間だけ突発的に通信量が増えた（バースト）ことは、グラフからは見えない。

> 「平均することの問題」→ **ピーク（バースト）が見えなくなる**。見たいなら、取得間隔を短くするか、しきい値監視・機械学習監視を併用する。

### 32ビットカウンタでカウンタラップが発生したとき、通信量を正しく計算するには、カウンタ値をどう補正する？
- 段階: 過去問
- 出典: R3 午後Ⅱ 問2 設問1(3)
- 本文: ◎
- 状況: 管理サーバは、SNMPで5分ごとにインタフェースのカウンタ値（32ビット）を取得している。時刻tの値をXt、5分前（t−1）の値をXt−1とする。t−1とtの間でカウンタラップが1回起きた。補正のしかたとして、今回の値 Xt に 2³² を足す、Xt に 2³²−1 を足す、前回の値 Xt−1 に 2³² を足す、Xt−1 に 2³²−1 を足す、の4通りを比べる。

**今回の値 Xt に 2³² を足して、Xt＋2³² に補正する。**

32ビットカウンタの値は 0 〜 2³²−1 の **2³² 通り**。上限の次は 0 に戻る。だからラップ後の Xt は、「本当の値」より **2³² 小さい**。足して戻す。

例（2³²＝4,294,967,296）：Xt−1＝4,294,967,000 のあと、1,000オクテット受信するとカウンタは **0に戻って** Xt＝704 になる。
- 補正して Xt＋2³² − Xt−1 ＝ 704 ＋ 4,294,967,296 − 4,294,967,000 ＝ **1,000** ✓

「−1」を付ける補正（Xt＋2³²−1、Xt−1＋2³²−1）は、0 も1つの値なので不正解。前回の値 Xt−1 に足す補正は、差がさらに小さくなって逆方向。

> カウンタラップの補正 → **ラップ後（小さくなった今回の値）に 2³² を足す**。

## しきい値監視・機械学習監視

### しきい値監視と機械学習監視は、何が違う？
- 段階: 知識
- 出典: R3 午後Ⅱ 問2 設問4

| | しきい値監視 | 機械学習監視 |
|---|---|---|
| 判断のしかた | 通信量などに **上限値・下限値を決めておく**。上回る・下回るとアラート | **過去の時系列データから、傾向や周期性を学習して、近い将来の値を予測**。予測値と実測値のずれで異常を検知 |
| 向いているもの | 回線の使い切り（輻輳）のように、**決まった値を超えたら困る** もの | 「いつもと違う」変化（急に増えた・減った）。曜日・時間帯の波があっても対応できる |
| 弱点 | 上限未満の異常（夜間の突然の増加など）、突発的な減少には気づきにくい | 学習に使う過去データが必要。何が異常かの意味づけは人が行う |

- **複数の種類のデータを組み合わせて** 監視すると、ネットワークの状況を素早く、詳細に把握できる
- 機械学習監視は、通信量（統計データ）だけでなく、**ログの量** など別の種類のデータにも使える

### 専用線2本を均等に使う。1本が障害になっても輻輳しないためには、平常時に各回線の何％を上限として、しきい値監視すればよい？
- 段階: 過去問
- 出典: R3 午後Ⅱ 問2 設問4(2)
- 本文: ○
- 状況: A社は、インターネット接続の専用線を2本に冗長化する。通信を均等に分散すると仮定すると、使える帯域幅は専用線2回線分。どちらかの専用線に障害が起きると、使える帯域幅は1回線分になる。専用線に流れるトラフィックの輻輳を避けるために、平常時から、それぞれの専用線で利用できる帯域幅のある割合（％）を、単位時間あたりの通信量の上限値として、しきい値監視する。

**50**（％）。

計算：1本の帯域を B、平常時に各回線が流す通信量を x とする（均等に分散）。
- 1本が故障すると、全通信 **2x が残りの1本に集まる**
- 輻輳しないためには、2x ≤ B → **x ≤ B／2 ＝ 50%**

だから、**平常時に各回線で帯域の50%を超えたらアラート**にしておけば、1本が故障しても残りの1本で受けきれる。アラートが出たら原因を調べ、必要なら専用線の増速を検討する。

> 冗長構成の上限値 → **障害で台数（回線）が減ったときに、残りで全部受けられる** 値。2本なら50%、3本なら 2/3 ≒ 66%（1本故障を想定）。

### 管理サーバの統計データとは別に、機械学習監視で使えるデータは？ それで検知できる、トラフィック異常とは別の異常は？
- 段階: 過去問
- 出典: R3 午後Ⅱ 問2 設問4(3)
- 本文: ○
- 状況: A社の管理サーバには、SNMPで集めた通信量などの統計データのほか、FWとプロキシサーバが SYSLOG で送ってくる通信ログのデータが保存されている。Cさんは、通信量（統計データ）の機械学習監視でトラフィック異常（突発的な増加・減少）を検知できることを確認した。さらに、統計データとは別のデータでも監視すると、トラフィック異常とは別の異常が検知できることを確認した。

データ：**FWとプロキシサーバの通信ログデータ**（25字以内）
検知内容：**単位時間当たりの通信ログデータ量が突発的に増えたり減ったりしたこと**（40字以内）

通信ログは、通信が1回あるたびに1行増える。**ログの量（単位時間あたりの行数）** も機械学習で監視すると、通信量（ビット）が目立たなくても、**接続の回数が異常** なこと（たとえば、不正な接続を大量に試みているなど）に気づける。

> 「統計データとは別のデータ」→ 本文に出てくる **ログ（FW・プロキシの通信ログ）**。「トラフィック異常とは別の異常」→ **通信ログの量の突発的な増減**（本文の字句で答える）。
