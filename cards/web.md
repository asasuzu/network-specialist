# Web・DNS・負荷分散

HTTP のバージョン、TLS、DNS、ロードバランサ、CDN。

## HTTPのバージョン

### HTTPの「リクエスト」と「レスポンス」とは？
- 段階: 基礎
- 出典: R7 午後Ⅰ 問2 設問3(2)e・f
- 本文: ◎

- **リクエスト**：ブラウザ → サーバ「このページ（画像）をください」
- **レスポンス**：サーバ → ブラウザ「はい、どうぞ」（中身と、200 OK などの結果）

HTTPは必ず「リクエストを送って、レスポンスが返る」の1往復が基本単位。

### HTTPのバージョンごとの違いをまとめると？
- 段階: 基礎

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 下の層 | TCP | TCP | **UDP（QUIC）** |
| 1本の接続で並列処理 | できない（順番待ち） | できる（ストリーム） | できる（ストリーム） |
| HTTPレイヤーのHoL | **あり** | なし | なし |
| TCPレイヤーのHoL | あり | **あり** | なし |
| コネクション数 | 多い | 少ない | 少ない |

どのバージョンを使うかは、最近のブラウザは HTTP/3 まで対応しているので、**主にサーバ側の対応しだい**。

### HTTP/1.1の問題点と、ブラウザの対処法は？
- 段階: 知識
- 出典: R7 午後Ⅰ 問2 ／ R5 午後Ⅰ 問1 設問2(1)

- 1本のTCPコネクションでは、**リクエストを送った順番どおりにレスポンスを返す** 必要がある → 1つ遅いと後ろが全部待つ（HTTPレイヤーのHoLブロッキング）
- 対処：ブラウザが **TCPコネクションを複数本同時に張って**、並行してダウンロードする

副作用：TCPコネクションの数が増える → **NAPT変換エントリーも増える**（R7 午後Ⅰ 問2 の論点）。

### HTTP/2で何が変わった？
- 段階: 知識
- 出典: R7 午後Ⅰ 問2 設問3(2)g・h ／ R5 午後Ⅰ 問1

**ストリーム** という仮想的な通信単位が導入された。

- 1本のTCPコネクションの中に、複数のストリームを作れる
- 各ストリームには **ストリームID** が付いていて、どのリクエストへの返事かを区別できる
- → 1本のTCPで **多重化・並列処理** ができる。HTTPレイヤーのHoLブロッキングが解消
- TCPコネクションの本数が少なくて済む → NAPT変換エントリーも少なくて済む

残る問題：TCP自体は1本なので、パケットが1つ失われると、再送されるまで全ストリームが待たされる（**TCPレイヤーのHoLブロッキング**）。

### HTTP/3で何が変わった？
- 段階: 知識
- 出典: R7 午後Ⅰ 問2

**TCPの代わりにUDPを使い、その上の QUIC というプロトコルでストリームを実現した。**

- ストリームごとに独立して再送するので、1つのパケットが失われても他のストリームは止まらない → **TCPレイヤーのHoLブロッキングも回避**
- 暗号化（TLS 1.3）がQUICに組み込まれている
- UDPの **443番** を使う

NAPTから見ると **UDPの通信** なので、終わりの合図がなく、保持時間が切れるまでエントリーが残る（IP・LANの基盤の「保持時間」のカードとつながる）。

### HTTP/2でどのプロトコルを使うかは、通信のどのタイミングで決める？
- 段階: 知識
- 出典: R5 午後Ⅰ 問1 設問2(2)・設問3(2)

**TLSのハンドシェイク中**（暗号化通信を始めるとき）に決める。この仕組みを **ALPN** という。

ブラウザが「HTTP/2 と HTTP/1.1 が使えます」と伝え、サーバがどちらを使うか選ぶ。TCPの上で何のプロトコルを話すかを、通信の最初に決めておける。

### HTTP/2は、ストリームの多重化のほかに何が改善された？
- 段階: 知識
- 出典: R5 午後Ⅰ 問1 設問1 d・e

- **ヘッダ圧縮**：HPACK というアルゴリズムで、毎回ほぼ同じ内容のヘッダ（Cookie など）を小さくして送る。HTTP/3 では QPACK
- **フロー制御**：**ストリームごと** に「受け取れる量」を決めて、1つのストリームが帯域やメモリを独占するのを防ぐ
- **バイナリ形式**：HTTP/1.1 のテキストではなく、バイナリのフレームで送る
- **暗号化**：仕様上はTLSなしでも使えるが（h2c）、ブラウザが使うのは **TLS上のHTTP/2（識別子 h2）**。h2 は TLS 1.2 以上が必要

### HoL（Head of Line）ブロッキングとは？ なぜ全部終わるまで時間がかかる？
- 段階: 過去問
- 出典: R7 午後Ⅰ 問2 設問3(1)
- 本文: ◎

**先の処理が終わるまで、後ろの処理が待たされるから。**

レジの行列で、先頭の人の会計が長引くと、後ろの人は全員待つしかない状態。直列で処理すると、1つ遅いものがあるだけで全体が遅れる。

> 「HoLブロッキングの問題は？」→ **先行が終わるまで後続が待たされる** と答える。

### HTTP/1.1で同じ測定データを送ると、やり取りするIPパケットが多くなる理由は？
- 段階: 過去問
- 出典: R7 午後Ⅱ 問2 設問4(3)
- 本文: ◎
- 状況: Y社のGメーターは、1日分24件の測定データを、CoAP（UDP）のPOSTで24回に分けて、Gメーター管理サーバに送る。同じことをHTTP/1.1（TCP）で行った場合と比べて、CoAPのほうが、やり取りされるIPパケットの数が少なく、測定データの通信時間が短くて済む。

**TCPコネクション確立とコネクション切断の処理が行われるから。**

HTTP/1.1はTCPの上で動くので、データを送る前後に、パケットが余分に必要になる。
- **確立**：3ウェイハンドシェーク（SYN → SYN/ACK → ACK）の3パケット
- **切断**：FINとACKのやり取り（4パケットほど）

CoAPは **UDP** で、コネクションを作らない。CON（要求）とACK（応答）の **2パケットだけ** で済む。24回送るのに、HTTP/1.1だと毎回（コネクションを使い回さなければ）確立と切断のパケットが加わり、パケット数も通信時間も増える。

### HTTP/2が、1本のTCPコネクションの中で複数のリクエスト／レスポンスを同時に進めるために使う、仮想的な通信路を何という？
- 段階: 過去問
- 出典: R5 午後Ⅰ 問1 設問1 d
- 本文: ◎

**ストリーム**

1本のTCPの中に複数のストリームを作り、リクエストとレスポンスの組をストリームごとに進める。各ストリームには **ストリームID**（クライアントが始めるものは奇数：1、3、5…）が付いていて、どの返事がどのリクエストのものか区別できる。フロー制御もストリームごとに行う。

### HTTP/2のリクエストに必須の疑似ヘッダフィールド（:scheme、:path と、あと1つ）は？
- 段階: 過去問
- 出典: R5 午後Ⅰ 問1 設問1 e
- 本文: ◎

**:method**

HTTP/1.1 で「GET /index.html HTTP/1.1」や Host ヘッダに書いていた情報を、HTTP/2 では「:」で始まる **疑似ヘッダフィールド** として書く。

| 疑似ヘッダ | 中身の例 |
|---|---|
| :method | GET、POST などのリクエストの種類 |
| :scheme | https |
| :path | /index.html |
| :authority | ホスト名（HTTP/1.1 の Host ヘッダに相当） |
| :status（レスポンス） | 200 など |

### HTTP/1.1のパイプラインで、複数のリクエストを続けて送ったとき、サーバはレスポンスをどんな順序で返さなければならない？
- 段階: 過去問
- 出典: R5 午後Ⅰ 問1 設問2(1)
- 本文: ◎
- 状況: 同じTCPコネクションの中で、HTTPリクエストを、前のレスポンスを待たずに続けて送る仕組み（HTTPパイプライン）がある。これにはサーバが返すレスポンスの順序に制約があるが、HTTP/2 ではその制約がない。

**リクエストを受けたのと同じ順序でレスポンスを返す必要がある。**

パイプラインは「返事を待たずに次のリクエストを送る」仕組みだが、返事は **送った順** でないと、どのリクエストへの返事か区別できない。だから先頭の処理が遅いと、後ろの返事も待たされる（HoLブロッキング）。

HTTP/2 は、ストリームIDで返事とリクエストを対応づけるので、順序の制約がなく、できた順に返せる。

> 「HTTP/1.1のパイプラインの制約は？」→ **レスポンスはリクエストと同じ順番**。HTTP/2 では解消、とセットで。

## DNS

### DNSの主なリソースレコード（A・NS・MX・SOAなど）は？
- 段階: 基礎
- 出典: R5 午後Ⅱ 問2 設問1

| レコード | 意味 |
|---|---|
| **SOA** | ゾーンの管理情報（プライマリのDNSサーバ、管理者、シリアル番号など）。ゾーンの先頭に1つ |
| **NS** | そのドメインを管理するDNSサーバの **ホスト名** |
| **MX** | そのドメイン宛のメールの配送先メールサーバの **ホスト名**。数値（優先度）が **小さいほど優先** |
| **A** | ホスト名 → IPv4アドレス |
| AAAA | ホスト名 → IPv6アドレス |
| CNAME | 別名（ホスト名 → 別のホスト名） |
| PTR | IPアドレス → ホスト名（逆引き） |
| TXT | 任意の文字列（SPFなどの送信ドメイン認証で使う） |

NSやMXの右側に書くのは **ホスト名**（IPアドレスではない）。そのホスト名のAレコードも、別の行で必要になる。

### DNSの「スタブリゾルバ」「フルサービスリゾルバ」「権威DNSサーバ」は何が違う？
- 段階: 基礎
- 出典: R4 午後Ⅰ 問3

| | 役割 |
|---|---|
| **スタブリゾルバ** | PCの中にある簡易な名前解決の部品。自分では調べず、**DNSサーバに「調べて」と丸投げ**（再帰問合せ）する |
| **フルサービスリゾルバ**（キャッシュDNS） | PCの代わりに、ルートから順にたどって答えを探す（再帰問合せを受け付ける）。結果は **キャッシュ** する |
| **権威DNSサーバ**（コンテンツDNS） | 自分が管理する **ゾーンの正しい情報を答える**。他のゾーンは調べない |

R4 午後Ⅰ 問3 の構成：
- 社内DNSサーバ：内部LANのゾーンを管理。それ以外の名前解決は外部DNSサーバに転送
- 外部DNSサーバ：DMZのゾーン管理（権威）と、フルサービスリゾルバの **両方** の機能。**社外からの再帰問合せは受け付けない**

社外からの再帰問合せまで受けると、誰でも使えるDNS（オープンリゾルバ）になり、**DNSを使った攻撃の踏み台** にされる。

### FQDNとは？ DNSでの名前解決とは？
- 段階: 基礎

- **FQDN**：ホスト名からドメイン名まで省略せずに書いた名前（例：`controller.example.com`）
- **名前解決**：FQDNから **IPアドレスを調べる** こと。DNSサーバに問い合わせる（UDP/53）

機器の設定にIPアドレスでなくFQDNを書いておくと、**接続先のサーバのIPアドレスが変わっても、DNSの登録を直すだけで済み、機器の設定を変えなくていい**。サーバの引っ越しや冗長化・負荷分散がしやすくなる。

### DNSサーバの3つの役割（権威サーバ・フルサービスリゾルバ・フォワーダ）は何が違う？
- 段階: 基礎
- 出典: R3 午後Ⅱ 問1

| 役割 | 何をするか |
|---|---|
| **権威DNSサーバ** | 自分が管理するドメインの「名前とIPアドレスの対応表（ゾーンファイル）」を持っていて、それについて **正式に答える** サーバ |
| **フルサービスリゾルバ**（キャッシュDNSサーバ） | PCに頼まれて、**権威サーバを順にたどって答えを探し**、結果を覚えておく（キャッシュ）サーバ。ISPが提供することが多い |
| **フォワーダ** | 自分で答えられない問い合わせを、**別のDNSサーバ（ISPのフルサービスリゾルバなど）に丸投げ（転送）する** 設定・機能 |

R3 午後Ⅱ 問1 の会社の例：
- 外部DNSサーバ（DMZ）：インターネットに公開するドメインの権威サーバ
- 内部DNSサーバ：社内ドメインの権威サーバ。社外ドメインの問い合わせは、フォワーダとしてISPのフルサービスリゾルバに転送。DHCPサーバも兼ねる

### 名前解決でAAAAレコードとAレコードは何が違う？ DNSサーバ自身にIPv6アドレスは必要？
- 段階: 知識
- 出典: R7 午後Ⅱ 問1

| レコード | 答えるもの |
|---|---|
| **A** | FQDN → **IPv4アドレス** |
| **AAAA**（クワッドA） | FQDN → **IPv6アドレス** |

- IPv4とIPv6の両方に対応するサイトなら、PCは **AとAAAAの両方** を問い合わせる
- 両方の答えが **ほぼ同時に** 届いたら、**IPv6を優先** して通信する
- DNSメッセージを運ぶ通信（PC ⇔ キャッシュDNSサーバ）が **IPv4でも、AAAAレコードは引ける**。だから、IPv6対応のためにキャッシュDNSサーバへIPv6アドレスを割り当てる必要は **ない**（R7 午後Ⅱ 問1 のR係長の説明）

### DNS応答（ANSWER・AUTHORITY・ADDITIONAL）はどう読む？ CNAMEとNSは何？
- 段階: 知識
- 出典: R7 午後Ⅱ 問1 設問3(2)

DNSの応答は3つの欄に分かれる。

| 欄 | 入っているもの |
|---|---|
| **ANSWER** | 問い合わせへの答えそのもの |
| **AUTHORITY** | そのゾーンを管理する **権威DNSサーバのNSレコード** |
| **ADDITIONAL** | 役に立つ **おまけ情報**（NSのFQDNのIPアドレスなど） |

主なレコード：
- **CNAME**：別名。「このFQDNは、あのFQDNの別名」と教える（`saas.example.com.` → `dual-saas.example.net.`）。応答は別名の先の名前で続く
- **NS**：このゾーンを管理している権威DNSサーバの **FQDN**
- **A / AAAA**：FQDNに対するIPv4 / IPv6アドレス

「**どのサーバが管理しているか**」はAUTHORITYの **NS**、「**アドレスは何か**」はANSWERの **A / AAAA** を読む。FQDNは最後の「.」まで含めて書く。

### MXレコードの「値」とは？ メールはどのサーバに送られる？
- 段階: 知識
- 出典: R6 午後Ⅱ 問2 設問1(3)

MXレコードの値は **Preference（優先度）**。**小さいほど優先** される。

例：`y-sha.com. MX 1 y-mail2.y-sha.com.` と `y-sha.com. MX 20 y-mail1.y-sha.com.` があれば、
- 平常時は **値が小さい y-mail2** に送られる
- y-mail2 が応答しないとき、**次の y-mail1** に送られる（冗長化）

値が同じなら、送信側が選ぶ（負荷分散になる）。

MXレコードに書くのは **ホスト名（FQDN）** で、IPアドレスは別に **Aレコード** で引く。

### DNSラウンドロビンとは？ TTLは長いほうがいい？ 短いほうがいい？
- 段階: 知識
- 出典: R6 午後Ⅱ 問2 設問1(2)

**1つのホスト名に、複数のIPアドレスのAレコードを登録しておき、問い合わせのたびに返す順番を入れ替えて、アクセスを振り分ける** 方法。

- 専用の負荷分散装置が要らない。簡単
- **弱点1**：サーバが落ちていても、そのIPアドレスを返し続ける（死活監視がない）
- **弱点2**：問い合わせた側が答えを **キャッシュ** していると、TTLが切れるまで同じサーバにだけ送り続ける → **偏る**

→ 偏りを小さくしたいなら、**TTLを短くする**。短いと、頻繁に問い合わせ直して、別のサーバが返ってくる。ただし、DNSサーバへの問い合わせが増える。

### DNSの正引きと逆引きとは？ PTRレコードは誰が書ける？
- 段階: 知識
- 出典: R6 午後Ⅱ 問2 設問1(5)

| | 引く向き | レコード |
|---|---|---|
| **正引き** | ホスト名（FQDN） → IPアドレス | A、AAAA |
| **逆引き** | IPアドレス → ホスト名（FQDN） | **PTR** |

逆引きの書式：`ホストのIPアドレス IN PTR ホストのFQDN`（実際は `4.3.2.1.in-addr.arpa.` の形で書く）。

PTRレコードを管理するのは **IPアドレスの持ち主**（ISPなど）。つまり **攻撃者も、自分が借りているIPアドレスの逆引きは自由に書ける**。そこに他社のドメイン名を書けば、「逆引きしたら正規のサーバ名が返ってくる」状態を作れてしまう。

→ 逆引きだけで送信元を信用してはいけない。

### DNSのメッセージは何バイトまで？ 大きいときは？
- 段階: 知識
- 出典: R6 午後Ⅱ 問2 設問3(1)

**UDPで送るときの上限は 512 バイト**（従来のDNS）。

- 答えが512バイトに入らないとき、応答に「切り詰めた」印（TCビット）が付く → 問い合わせ側は **TCP/53** でやり直す
- 長いTXTレコードがあると、UDPに収まらなくなる
- 512バイトを超える応答をUDPで送る拡張（EDNS0）もあるが、この試験では「UDPは512バイト」と覚えておけばよい

R6 午後Ⅱ 問2：DKIMの公開鍵をTXTレコードに載せるので、**512バイトに収まる鍵長（一般に2,048ビット）** が使われる。

### DNSラウンドロビンの弱点は？ 障害が起きたらどうする？
- 段階: 知識
- 出典: R5 午後Ⅱ 問1 設問1(1)・(3)

DNSラウンドロビンは、**サーバが生きているかどうかを確認しない**。サーバが故障しても、そのサーバのIPアドレスを返し続けるので、順番が回ってきた利用者は接続に失敗する。

そのため障害時は、**故障したサーバのAレコードをゾーンファイルから削除する**（人が書き換える）必要がある。書き換えても、キャッシュDNSサーバのキャッシュ（TTL）が切れるまでは反映されないので、**TTLを平常時から短くしておく**。

R5 午後Ⅱ 問1 の案2（プロキシサーバBとCの両方に、同じ名前で2つのAレコード）：Bが故障したら、Bの192.168.1.145のレコードを消して、Cの192.168.2.145だけにする。

> 「DNSで切り替える」系の問題 →「**DNS自身は障害を検知しない**（監視は別に必要）」「**書き換えても TTL の間は反映されない**」の2つをセットで考える。

### インターネット向けと社内向けで、DNSが返すIPアドレスを分けるのはなぜ？
- 段階: 知識
- 出典: R5 午後Ⅱ 問2 設問1

同じサーバ（ホスト名）でも、**見る人の場所によって届くアドレスが違う** から。

| 向け | 返すアドレス | 理由 |
|---|---|---|
| インターネット向けドメイン（example.jp） | **グローバルIPアドレス** | インターネットからはプライベートIPアドレスに届かない。ルータ/FWの **静的NATで変換される側の（変換前の）アドレス** を書く |
| 社内向けドメイン（y-sha.example.lan） | **プライベートIPアドレス** | 社内からは、変換せずサーバへ直接届く |

### DNSの再帰問合せで、送信元ポート番号をランダム化するのはなぜ？
- 段階: 知識
- 出典: R4 午後Ⅰ 問3

**DNSキャッシュポイズニング**（偽の応答をキャッシュに覚え込ませる攻撃）への対策。

### SRVレコードとは？ Priority と Weight の意味は？
- 段階: 知識
- 出典: R4 午後Ⅰ 問3

**サービス名とドメインで問い合わせると、そのサービスを提供しているホスト名とポート番号を教えてくれる DNSのレコード。**

書式：`_サービス名._プロトコル.ドメイン  TTL  IN  SRV  Priority  Weight  Port  Target`
例：`_kerberos._tcp.example.jp  43200  IN  SRV  120  2  88  DS1.example.jp.`

| 項目 | 意味 |
|---|---|
| Priority | **優先度**。**値が小さいものが先に使われる**。複数あるときの選び方 |
| Weight | **Priorityが同じとき**の使用比率。値が大きいほど多く使われる |
| Port | サービスのポート番号 |
| Target | サービスを提供するホスト名（Aレコードで名前解決する） |

メリット：PCにサーバの名前やポート番号を設定しなくても、DNSからサービスの場所を見つけられる。サーバの追加・変更もDNS側で済む。

### DNSラウンドロビンとは？ 使用比率を偏らせたいときは？
- 段階: 知識
- 出典: R4 午後Ⅰ 問3 設問3(3)

**同じホスト名に複数のAレコードを登録し、問合せのたびに返す順番を入れ替えて、アクセスを分散する** 仕組み。

- 各サーバが選ばれる確率は **ほぼ同じ**（均等）
- サーバの状態（故障、負荷）は見ない
- 比率を偏らせたいときは、**同じIPアドレスのAレコードを複数登録** する（2対1にしたいなら、片方を2つ、もう片方を1つ）

### DNSのTTLとは？ 長いとどうなる？
- 段階: 知識
- 出典: R4 午後Ⅰ 問3 設問3(2)

**TTL ＝ DNSの応答を、キャッシュに保持してよい時間（秒）。** 過ぎたら、もう一度問い合わせる。

| | 長い | 短い |
|---|---|---|
| 問合せの数 | 少ない（DNSの負荷が小さい） | 多い |
| 設定を変えたとき | **反映が遅い**（古い情報がキャッシュに残る） | 反映が早い |

秒を分に直すとき：÷60。43,200秒 ＝ 720分 ＝ 12時間。

### Webサイトにアクセスするとき、DNSの問い合わせはどう流れる？ 権威DNSサーバには何が届く？
- 段階: 知識
- 出典: R3 午後Ⅱ 問1 設問6(6)

1. 利用者のPCが、設定された名前解決要求先（フルサービスリゾルバ）に「www.example.jp のIPアドレスは？」と聞く

### DNSメッセージが大きいときは、UDPのほかに何で送る？ EDNSとは？
- 段階: 過去問
- 出典: R7 午後Ⅱ 問1 設問3(1)h
- 本文: ◎
- 状況: Q社のキャッシュDNSサーバは、権威DNSサーバと通信するとき、512バイトを超えるDNSメッセージをEDNSの範囲内ではUDPで送受信する。EDNSが使えないときや、調整した最大のメッセージサイズを超えるときは、別のプロトコルで送受信することになる。

**TCP**。

- 従来のDNSは、UDPで送れるメッセージの上限が **512バイト**
- IPv6はAAAAレコードなどで大きくなりやすい
- **EDNS（EDNS(0)、RFC 6891）** は、「自分は512バイトより大きなUDPのメッセージを受け取れる」と相手に伝えて、**上限を広げる** 拡張
- 広げた上限も超えるときや、相手がEDNSに対応していないときは、**TCPで送り直す**（応答が切り捨てられたことを示す印が付き、クライアントがTCPでやり直す）

DNSのポートは UDP/53 が基本で、**TCP/53** もある（ポート番号のカードを参照）。

> 「DNSで大きいメッセージ」→ 基本はUDP、**収まらないときはTCP**。ファイアウォールではTCP/53も許可が必要。

### 攻撃者が、PTRレコードに行う不正な操作は？

### DNSをUDPで使うときのメッセージの最大長は？ なぜ2,048ビットの鍵がよく使われる？
- 段階: 過去問
- 出典: R6 午後Ⅱ 問2 設問3(1)h・i
- 本文: ◎

**h：UDP、i：512（バイト）**

DNSのメッセージは、UDPでは最大 **512バイト**。DKIMの公開鍵はTXTレコードに入れるので、この中に収まらなければならない。2,048ビットのRSA公開鍵（Base64で約400文字）なら収まるが、4,096ビットだと約740文字になって収まらない。だから一般に2,048ビットが使われる。

> DNSの **UDP は512バイト**（これを超えるとTCPでやり直す。EDNS0という拡張を使えば、UDPでも512バイトを超えられる）。DKIMの鍵長が2,048ビットにとどまる理由として出る。

### プロキシサーバのDNS名のAレコードのTTLを、平常時から小さくするのはなぜ？

## TLS・DTLS

### DTLSとは？ TLSと何が違う？
- 段階: 基礎
- 出典: R7 午後Ⅱ 問2

**DTLS**（Datagram TLS）＝ **TLSを、UDPの上で使えるようにした** 暗号化プロトコル。

- TLSは、TCP（順番どおり・再送あり）を前提にしている。UDPでは **順番の入れ替わり・消失** が起きるので、そのままでは動かない
- DTLSは、TLSに **再送や順序の管理** などを足して、UDPでも動くようにした
- 使われるところ：CoAP、VoIPなど、UDPを使うリアルタイム・軽量な通信
- バージョンの対応：DTLS 1.2 ≒ TLS 1.2、**DTLS 1.3 ≒ TLS 1.3**（RFC 9147）

UDPで使うので、**送信元を偽装したハンドシェークによる攻撃** への対策が要る（DTLS 1.3 の cookie。次のカード）。

### HTTPS（TLS）の通信は、どんな順番で始まる？
- 段階: 基礎
- 出典: R5 午後Ⅰ 問1 設問3(1)

1. **TCP 3ウェイハンドシェイク**：SYN → SYN/ACK → ACK（つなぐ準備）
2. **TLS ハンドシェイク**：
   - クライアントが **ClientHello**：使えるTLSのバージョンや暗号方式、ALPN（使いたいプロトコルの一覧）などを伝える
   - サーバが **ServerHello**：その中から選んだものを返す。続けて証明書を送り、鍵を交換して暗号化を始める
3. **暗号化されたHTTPの通信**（HTTP/2ならストリームごとにリクエスト／レスポンス）

「TCPでつなぐ → TLSで暗号化の約束をする → HTTPをやり取りする」の順。ALPN のような **TLSの拡張** は、ClientHello と ServerHello のやり取りの中で交換される。

### TLS 1.3 のハンドシェイクは、どんな順番でやり取りする？ クライアント証明書はどこで送られる？
- 段階: 知識
- 出典: R4 午後Ⅱ 問1 図3

TCPの3ウェイハンドシェイクのあとに、TLSのやり取りが始まる。**クライアント証明書で認証するとき** の流れ：

| 向き | メッセージ | 役割 |
|---|---|---|
| クライアント → サーバ | **ClientHello** | 使えるバージョン・暗号方式、鍵交換の材料を送る |
| サーバ → クライアント | **ServerHello** | 使う暗号方式を決め、鍵交換の材料を返す（ここから先は暗号化される） |
| サーバ → クライアント | EncryptedExtensions | 追加の設定 |
| サーバ → クライアント | **CertificateRequest** | 「クライアント証明書を出してください」 |
| サーバ → クライアント | **Certificate** | **サーバ証明書** |
| サーバ → クライアント | **CertificateVerify** | サーバが秘密鍵を持っている証拠（署名） |
| サーバ → クライアント | Finished | ここまでのやり取りが改ざんされていない確認 |
| クライアント → サーバ | **Certificate** | **クライアント証明書** |
| クライアント → サーバ | **CertificateVerify** | クライアントが秘密鍵を持っている証拠（署名） |
| クライアント → サーバ | Finished | 同上 |

終わると暗号化通信（SSL-VPNなら、トンネル）が使える。

### TLSの鍵交換方式（RSA、DHE、ECDHE）の違いは？ 「前方秘匿性」とは？
- 段階: 知識
- 出典: R4 午後Ⅱ 問1

| 方式 | 仕組み | 秘密鍵が漏えいしたとき |
|---|---|---|
| **RSA鍵交換** | クライアントが作った秘密の値を、サーバの **RSA公開鍵で暗号化** して送る | 過去に録画された通信も **まとめて復号される** |
| 静的DH | サーバが **固定のDH公開鍵** を使い続ける | 同上 |
| **DHE／ECDHE** | **通信のたびに新しい鍵（使い捨て）** でDH鍵交換をする（E = Ephemeral） | **過去の通信は復号されない** |
| PSK | 事前に共有した鍵を使う | ― |

**前方秘匿性（PFS）** ＝ 長期に使う秘密鍵が将来漏れても、過去の通信は解読されない性質。DHE/ECDHE にはある。

TLS 1.3 で使える鍵交換は **DHE、ECDHE、PSK** の3つ。RSA鍵交換と静的DHは廃止された。

### DTLS 1.3のcookieは、サーバに何を判断させる？ 不正だったらどうする？
- 段階: 過去問
- 出典: R7 午後Ⅱ 問2 設問3(6)
- 本文: ○
- 状況: DTLS 1.3では、ClientHelloを受け取ったDTLSサーバが、HelloRetryRequestにcookieを添えて返す。クライアントは、受け取ったcookieを添えて、ClientHelloをもう一度送る。DTLSサーバは、2回目のClientHello（図6(2)の(ⅲ)）に添付されたcookieを検査する。

**cookieが正しい場合に判断できること：(ⅰ)のClientHelloの送信元が、偽装されたものでないこと。cookieが不正な場合の対応：(ⅳ)のServerHelloを送信せず、ハンドシェークを終了する。**

流れ（図6(2)）：
1. (ⅰ) クライアント → ClientHello
2. (ⅱ) サーバ → **HelloRetryRequest ＋ cookie**（**小さいメッセージ**。送信元アドレスに送る）
3. (ⅲ) クライアント → **cookie を添えて** ClientHello をもう一度
4. (ⅳ) サーバ → cookieが正しければ ServerHello（以下、省略）

なぜ偽装が見破れるか：cookieは、**ClientHelloの送信元アドレスに届いて初めて手に入る**。送信元を偽装した攻撃者には（返事が標的に飛んでいくので）cookieが届かず、(ⅲ)を返せない。cookieが正しければ、送信元は **本当にその場所にいる** と分かる。しかも、最初の(ⅱ)は小さいので、**増幅も防げる**。

> 「cookieで何を確かめる？」→ **送信元アドレスが偽装でないこと**。偽装なら **ServerHello（大きい応答）を送らずに打ち切る**。

### ALPN（Application-Layer Protocol Negotiation）は、どのプロトコルの拡張機能？

### TLS 1.3 で使える鍵交換方式は、ECDHE、PSKと、あと何？

### TLS1.3で必須の AEAD 暗号利用モードでは、同時にどんな2つのセキュリティ処理が行われる？

**暗号化** と **メッセージ認証**（改ざん検知）。

AEAD（Authenticated Encryption with Associated Data）は、名前の通り「認証付き暗号」。暗号化と、データが改ざんされていないかの確認を **1回の処理で同時に** 行う。AES-GCM や ChaCha20-Poly1305 が代表例。

### RSA鍵交換や静的DH鍵交換で、秘密鍵が漏えいしたとき、広く復号されてしまう通信は何？
- 段階: 過去問
- 出典: R4 午後Ⅱ 問1 設問3(4)
- 本文: ○
- 状況: TLS 1.3 より前の鍵交換には、サーバのRSA秘密鍵を使う方式（RSA鍵交換）と、DH公開鍵を固定で使う方式がある。本文では、秘密鍵が漏えいしたときに、TLS 1.3 で使える方式に比べて、不正に復号される通信の範囲が広いと述べている。

**秘密鍵が漏えいする前に行われた通信のデータ。**

RSA鍵交換などでは、サーバの **固定の秘密鍵** で、通信の鍵が決まる。攻撃者が通信を録画しておき、**あとで秘密鍵を盗めば、過去の通信を全部復号できる**。DHE/ECDHE は通信ごとに使い捨ての鍵なので、秘密鍵が漏れても、漏えい前の通信には影響しない（前方秘匿性）。

> 「秘密鍵が漏れたら？」→ **過去の通信まで遡って復号される** か、**漏れた後の通信だけ** か、で方式の違いを答える。

## ロードバランサ

### ロードバランサ（LB）は何をする装置？ 仮想IPアドレスとは？
- 段階: 基礎
- 出典: R5 午後Ⅱ 問2

**複数のサーバの前に置いて、クライアントからのリクエストを振り分ける** 装置。サーバを増やしても、クライアントから見える入口は1つのまま。

- **仮想IPアドレス（VIP）**：クライアントが宛先にするアドレス。LBがこれ宛ての通信を受け取り、実際のサーバに振り分ける（LB自身の物理IPアドレスとは別）
- 持つ機能：**負荷分散**（誰に振り分けるか）、**セッション維持**（同じ人は同じサーバへ）、**ヘルスチェック**（故障したサーバを外す）

| | L4 LB | L7 LB |
|---|---|---|
| 判断に使う情報 | IPアドレス・ポート番号 | **HTTPの中身**（URL、Cookie、ヘッダ） |

R5 午後Ⅱ 問2：既設のECサーバのアドレス（192.168.1.2）をLBの仮想IPアドレスにして、ECサーバのアドレスは別に付け替えた。

### L4ロードバランサ（ネットワークモード）とL7ロードバランサ（アプリケーションモード）は、何が違う？
- 段階: 知識
- 出典: R5 午後Ⅰ 問1 設問4(2)

| | L4（レイヤー4）／ネットワークモード | L7（レイヤー7）／アプリケーションモード |
|---|---|---|
| 見るもの | IPアドレスとポート番号 | HTTPの中身（URL、ホスト名、ヘッダ、Cookie） |
| できること | 接続をそのままサーバに振り分ける。速い | URLごとの振り分け、HTTP/2 → HTTP/1.1 のような **プロトコルの変換**、TLSの終端 |
| 弱いところ | 中身を見ないので、URLで振り分け先を変えられない | 中身を読む分、処理が重い |

L4は通信を「そのまま」中継するだけなので、クライアントがHTTP/2で話しかけてきたら、サーバ側もHTTP/2で受けられなければならない。

> 「LBの動作モードは？」→ **URLを見て振り分けたい・プロトコルを変換したい** ならL7（アプリケーションモード）。

### スケールアップとスケールアウトの違いは？ サイトを止めずに増強できるのは？
- 段階: 知識
- 出典: R5 午後Ⅱ 問2 設問3(1)

| | スケールアップ | スケールアウト |
|---|---|---|
| やり方 | **1台の性能を上げる**（CPU・メモリの増設、上位機種へ交換） | **サーバの台数を増やす** |
| サービス停止 | 交換・増設のために **止める必要がある** | 新しいサーバを追加するだけ。**止めずに増強できる** |
| 上限 | 1台で出せる性能の限界がある | 台数を増やせば伸ばせる |
| 必要なもの | 特になし | **負荷分散装置（LB）** で振り分ける |
| 冗長性 | 1台なので、故障すると全断 | 1台が故障しても、残りで動かせる |

### LBでソースNATを「行う」場合と「行わない」場合は何が違う？
- 段階: 知識
- 出典: R5 午後Ⅱ 問2 設問3(3)・設問4

LBが振り分けるとき、**送信元IPアドレスを LB 自身のアドレスに書き換えるか** どうか。

| | ソースNATなし | ソースNATあり |
|---|---|---|
| サーバから見た送信元 | **クライアントの本当のIP** | **LBのIP** |
| 戻りの通信 | サーバのデフォルトゲートウェイを **LBにしておく** 必要がある（そうしないと、戻りがLBを通らず通信が成立しない） | サーバはLBに返すので、**サーバの設定変更が不要** |
| 困ること | LB以外の機器からサーバへの通信が、デフォルトゲートウェイ（LB）に返されてしまう（LBはルータではないので転送できない） | **アクセス元IPがログに残らない**（X-Forwarded-Forで補う） |

R5 午後Ⅱ 問2 では、**ソースNATなし** だと、運用PCからECサーバに直接アクセスする保守ができなくなる。そこで **ソースNATあり**＋サーバのデフォルトゲートウェイは元のまま、に方針を変えた。

### LBの負荷分散方式にはどんなものがある？ なぜ動的方式を選ぶ？
- 段階: 知識
- 出典: R5 午後Ⅱ 問2 設問5

| 種類 | 方式 | 中身 |
|---|---|---|
| 静的 | ラウンドロビン | 順番に振り分ける |
| 静的 | 重み付けラウンドロビン | 性能に応じた比率で順番に振り分ける |
| 動的 | 最小接続数 | 接続数が一番少ないサーバへ |
| 動的 | 最小応答時間 | 応答が一番速いサーバへ |
| 動的 | **エージェント方式** | サーバに入れたエージェントがCPU・メモリなどの負荷を伝え、それを見て振り分ける |

R5 午後Ⅱ 問2 で動的方式を選んだ理由：**リクエストの内容によって、サーバにかかる負荷が大きく違う** から。件数を均等にするだけでは偏る。

### セッション維持の方式（アクセス元の識別方法）にはどんなものがある？
- 段階: 知識
- 出典: R5 午後Ⅱ 問2 設問5(1)(2)

セッション維持 ＝ **同じアクセス元からのリクエストを、セッションの間は同じサーバへ送る** 機能。ログイン状態などをサーバが覚えているため、サーバが変わると続きが使えなくなる。

| 識別方法 | 困ること |
|---|---|
| **送信元IPアドレス** | NAPTやプロキシの後ろの **複数の人が同じIP** になり、同じサーバに偏る（R5：会員企業の複数の購買担当者が、同じ送信元IPになる） |
| **IPアドレス＋ポート番号** | **TCPコネクションが切れて再接続すると、ポート番号が変わる**。別のアクセス元だと見なされ、維持できない |
| **Cookie**（セッションID） | 利用者（ブラウザ）を正確に識別できる。LBがHTTPの中身を見る必要がある（HTTPSなら復号が必要） |

R5 午後Ⅱ 問2 は **セッションIDとサーバの対応表（セッション管理テーブル）** をLBが作る方式。

### ヘルスチェックのレイヤー3・4・7方式は何が違う？
- 段階: 知識
- 出典: R5 午後Ⅱ 問2 設問5(3)

LBが、振り分け先のサーバが **正常に動いているか** を定期的に調べて、障害のサーバを振り分け対象から外す。

| 方式 | 調べ方 | 検知できるもの |
|---|---|---|
| レイヤー3 | pingなど（ICMP） | サーバ（OS・ネットワーク）の停止 |
| レイヤー4 | ポートにTCPで接続できるか | 上に加えて、プロセスの停止（ポートが閉じる） |
| **レイヤー7** | **HTTPリクエストを送り、応答の内容（ステータスコードなど）を確認** | 上に加えて、**サービスとして正しく応答できない状態** |

> 「レイヤー3・4ではダメな理由」→「**サービスが稼働しているか（アプリが正しく応答するか）までは検査しないから**」。

### X-Forwarded-For とは？
- 段階: 知識
- 出典: R5 午後Ⅱ 問2 設問4(4)

**HTTPリクエストのヘッダに追加するフィールド**。LBやプロキシが、**元のクライアントのIPアドレス** を書き込んで、サーバに渡す。

- ソースNATやプロキシを通すと、サーバから見た送信元IPは **LB・プロキシのIP** になる
- そこでLB・プロキシが `X-Forwarded-For: クライアントのIP` を付けておけば、サーバのログに **本当のアクセス元** を残せる
- 複数の機器を経由すると、通ったIPがカンマ区切りで追記される

HTTPヘッダを書き換えるので、HTTPSの場合はLBが **復号（TLS終端）** している必要がある。

### TLS終端（SSLオフロード）とは？ 証明書はどこに置く？
- 段階: 知識
- 出典: R5 午後Ⅱ 問2 設問4(5)

**LBがクライアントとのHTTPS（TLS）を代わりに受けて、復号する** こと。

- サーバ証明書と **秘密鍵はLBに置く**（クライアントはLBと暗号化通信をする）
- LBがHTTPの中身（Cookie、URL、ヘッダ）を見られる → **Cookieでのセッション維持、X-Forwarded-Forの追加、レイヤー7のヘルスチェック** ができる
- サーバのTLS処理の負荷が減る。サーバを増設しても **証明書をインストールし直さなくてよい**（LBの1か所で管理）

LBからサーバまでをHTTPのままにするか、再度暗号化するかは構成による。

### リバースプロキシは、どうやって複数のWebAPに振り分ける？ ヘルスチェックは何のため？
- 段階: 知識
- 出典: R4 午後Ⅱ 問2

HTTPのリバースプロキシは、**リクエストの中身（L7）を見て振り分け先を決める**。

- 同じIPアドレス・同じポートに、複数のAPのリクエストが来る
- HTTPリクエストの **Hostヘッダ**（アクセスしたFQDN）で、どのAPかを識別する
- AP1つに対して振り分け先を **複数** 指定できる → 振り分け先を増やすと処理能力が上がり、1台あたりの負荷が減る
- **ヘルスチェック**：振り分け先が正常かを定期的に確認し、**異常な振り分け先は対象から外す**（利用者に障害を見せない）

Hostヘッダが使えない（HTTPではない独自プロトコルの）通信は、この方法では識別できない（R4 午後Ⅱ 問2 設問3(2) へ）。

### クラウドの仮想LBに設定する動作モードは、ネットワークモード（L4）とアプリケーションモード（L7）のどちらが適切？ その理由は？

### ソースNATをしないとき、既設ECサーバのデフォルトゲートウェイはどの機器からどの機器へ変更する？

### LBがECサーバ宛てのHTTPヘッダにX-Forwarded-Forを追加するのは何のため？
- 段階: 過去問
- 出典: R5 午後Ⅱ 問2 設問4(4)
- 本文: ○
- 状況: Y社のECサーバは、アクセス元のIPアドレスなどをログとして管理している。LBでソースNATを行うと、運用PCからECサーバへの通信もできるようになるが、ECサーバから見た送信元IPアドレスが変わる。そこで、ECサーバ宛てに送信するHTTPヘッダにX-Forwarded-Forフィールドを追加する。

**ECサーバに、アクセス元PCのIPアドレスを通知するため**

ソースNATを行うと、ECサーバから見た送信元IPアドレスが **全部LBのIPアドレス** になり、ECサーバのログから誰がアクセスしたか分からなくなる。LBがHTTPヘッダに **元のクライアントのIPアドレス** を書き込んで渡せば、ECサーバはそれをログに残せる。

### LBを導入したとき、増設ECサーバにサーバ証明書をインストールせずに済ませるには？
- 段階: 過去問
- 出典: R5 午後Ⅱ 問2 設問4(5)
- 本文: ○
- 状況: Y社のECサーバには、サーバ証明書が1つ登録されている。LBを導入して既設ECサーバに加え増設ECサーバ2台にも振り分けるが、増設ECサーバにはサーバ証明書をインストールせず、既設ECサーバのサーバ証明書を流用して対応したい。

**既設ECサーバにインストールされているサーバ証明書と秘密鍵のペアを、LBに移す。**

クライアントとのHTTPSを **LBが終端（復号）** する構成にする。LBが復号すれば、HTTPの中身（Cookie、ヘッダ）を見られるので、セッション維持・X-Forwarded-Forの追加・レイヤー7のヘルスチェックができる。

サーバ証明書は **秘密鍵とセットで** 使うので、**証明書と秘密鍵のペアをLBに** 入れる。こうすれば、ECサーバを増やしても、増設サーバに証明書を入れ直さなくてよい。

> 「サーバ証明書」と聞かれたら、**証明書だけでなく秘密鍵もセット** で答える。

### IPアドレスとポート番号の組合せでアクセス元を識別すると、セッション維持できなくなるのはなぜ？
- 段階: 過去問
- 出典: R5 午後Ⅱ 問2 設問5(1)
- 本文: ◎

**TCPコネクションが再設定されるたびに、ポート番号が変わる可能性があるから**

クライアントの送信元ポート番号は、TCPコネクションを張るたびに（ランダムに）決まる。コネクションが切れて再接続すると、**ポート番号が変わるので、LBは別のアクセス元と判断して別のサーバに振り分けてしまう**。ログイン状態などが引き継がれなくなる。

### LBがセッション管理テーブルに新しいレコードを登録するのはどんなとき？
- 段階: 過去問
- 出典: R5 午後Ⅱ 問2 設問5(2)
- 本文: ○
- 状況: Y社のLBは、Cookieの中のセッションIDと、振り分け先のECサーバの対応をセッション管理テーブルに記録して、セッションを維持する。ECサーバは、最初のアクセスの応答時に、ランダムなセッションIDをCookieに書き込んで返す。

**サーバからの応答に含まれる Cookie 中のセッションIDが、セッション管理テーブルに存在しない場合**

流れ：
1. クライアントが最初のリクエストを送る → LBがサーバに振り分ける
2. サーバが応答に **Cookie（セッションID）** を書き込む
3. LBは、そのセッションIDがテーブルに **なければ新規セッションと判断** して、「セッションID ⇔ 振り分け先サーバ」を **登録** する
4. 以降、リクエストのCookieのセッションIDがテーブルにあれば、**同じサーバに振り分ける**

### レイヤー3・4方式のヘルスチェックでは、なぜ適切な監視ができない？

### 共用リバースプロキシが、リクエストを送ってきたWebAPを識別するのは、どのヘッダフィールド？
- 段階: 過去問
- 出典: R4 午後Ⅱ 問2 設問2(2)
- 本文: ◎
- 状況: U社の共用リバースプロキシは、複数のWebAP（ap0.u-sha.com、ap1.u-sha.com など）のリクエストを、同じIPアドレスのTCP/80で受け付ける。そして、リクエストの情報から、WebAPが動作するWebAPコンテナへ振り分ける。

**ホストヘッダフィールド**（Host）。

どのAPも同じIPアドレス・同じポート（80）に届くので、IPアドレスとポートでは区別できない。HTTPリクエストの Host ヘッダに、ブラウザがアクセスしたFQDN（ap0.u-sha.com など）が入っているので、それで識別する。

> 「同じIP・同じポートで複数のWebサイトを区別」→ **Hostヘッダ**。

### PCがWebAPにアクセスするとき、DNSで取得する接続先IPアドレスと、共用リバースプロキシが振り分けるポート番号は？
- 段階: 過去問
- 出典: R4 午後Ⅱ 問2 設問2(3)
- 本文: △
- 状況: U社のPCが、WebAPの ap0.u-sha.com にアクセスする。DNSには、WebAPコンテナの前段にある共用リバースプロキシ（192.168.0.98）が登録されている。共用リバースプロキシは、振り分けルールの表に従い、コンテナサーバa（192.168.0.112）とコンテナサーバb（192.168.0.113）のうち、AP0のWebAPコンテナに振り分ける。

- オ：**192.168.0.98**（共用リバースプロキシのIPアドレス）
- カ：**8000**（振り分けルールで、AP0の振り分け先が「192.168.0.112:8000」「192.168.0.113:8000」だから）

図のつながり方（要点）：

### 同じポート番号を使う専用APが複数あるとき、負荷分散機能にはどんな仕組みが必要？
- 段階: 過去問
- 出典: R4 午後Ⅱ 問2 設問3(2)
- 本文: ○
- 状況: U社の専用APは、TCP/IPを使った独自のプロトコルで、PCからアクセスされ、同じポート番号を使うものがいくつかある。共用リバースプロキシはHTTPのHostヘッダでWebAPを識別していたが、専用APにはこの方法が使えない。

**複数のIPアドレスを設定し、IPアドレスごとに専用APを識別する仕組み。**

- Hostヘッダが使えない（HTTPではない）
- ポート番号も同じなので、ポートでも区別できない
- → 残るのは **宛先IPアドレス**。負荷分散装置に **APの数だけIPアドレス** を持たせ、「このIPアドレス宛て → この専用AP」と振り分ける

> 負荷分散で「APを識別する材料」→ **HTTPならHostヘッダ、HTTP以外なら宛先IPアドレス（かポート番号）**。
