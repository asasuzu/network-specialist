# Web・HTTP

HTTP/1.1・HTTP/2・HTTP/3 の違いと、HoLブロッキング。令和7年度 B-1 問2 から作成。

## HTTPのバージョン

### HTTPの「リクエスト」と「レスポンス」とは？
- 段階: 基礎
- 出典: R7 B-1 問2 設問3(2)e・f
- 本文: ◎

- **リクエスト**：ブラウザ → サーバ「このページ（画像）をください」
- **レスポンス**：サーバ → ブラウザ「はい、どうぞ」（中身と、200 OK などの結果）

HTTPは必ず「リクエストを送って、レスポンスが返る」の1往復が基本単位。

### HoL（Head of Line）ブロッキングとは？ なぜ全部終わるまで時間がかかる？
- 段階: 過去問
- 出典: R7 B-1 問2 設問3(1)
- 本文: ◎

**先の処理が終わるまで、後ろの処理が待たされるから。**

レジの行列で、先頭の人の会計が長引くと、後ろの人は全員待つしかない状態。直列で処理すると、1つ遅いものがあるだけで全体が遅れる。

> 💡 型：「HoLブロッキングの問題は？」→ **先行が終わるまで後続が待たされる** と答える。

### HTTP/1.1の問題点と、ブラウザの対処法は？
- 段階: 知識
- 出典: R7 B-1 問2 ／ R5 B-1 問1 設問2(1)

- 1本のTCPコネクションでは、**リクエストを送った順番どおりにレスポンスを返す** 必要がある → 1つ遅いと後ろが全部待つ（HTTPレイヤーのHoLブロッキング）
- 対処：ブラウザが **TCPコネクションを複数本同時に張って**、並行してダウンロードする

副作用：TCPコネクションの数が増える → **NAPT変換エントリーも増える**（R7 B-1 問2 の論点）。

### HTTP/2で何が変わった？
- 段階: 知識
- 出典: R7 B-1 問2 設問3(2)g・h ／ R5 B-1 問1

**ストリーム** という仮想的な通信単位が導入された。

- 1本のTCPコネクションの中に、複数のストリームを作れる
- 各ストリームには **ストリームID** が付いていて、どのリクエストへの返事かを区別できる
- → 1本のTCPで **多重化・並列処理** ができる。HTTPレイヤーのHoLブロッキングが解消
- TCPコネクションの本数が少なくて済む → NAPT変換エントリーも少なくて済む

残る問題：TCP自体は1本なので、パケットが1つ失われると、再送されるまで全ストリームが待たされる（**TCPレイヤーのHoLブロッキング**）。

### HTTP/3で何が変わった？
- 段階: 知識
- 出典: R7 B-1 問2

**TCPの代わりにUDPを使い、その上の QUIC というプロトコルでストリームを実現した。**

- ストリームごとに独立して再送するので、1つのパケットが失われても他のストリームは止まらない → **TCPレイヤーのHoLブロッキングも回避**
- 暗号化（TLS 1.3）がQUICに組み込まれている
- UDPの **443番** を使う

NAPTから見ると **UDPの通信** なので、終わりの合図がなく、保持時間が切れるまでエントリーが残る（IP・LANの基盤の「保持時間」のカードとつながる）。

### HTTP/2でどのプロトコルを使うかは、通信のどのタイミングで決める？
- 段階: 知識
- 出典: R5 B-1 問1 設問2(2)・設問3(2)

**TLSのハンドシェイク中**（暗号化通信を始めるとき）に決める。この仕組みを **ALPN** という。

ブラウザが「HTTP/2 と HTTP/1.1 が使えます」と伝え、サーバがどちらを使うか選ぶ。TCPの上で何のプロトコルを話すかを、通信の最初に決めておける。

### HTTPのバージョンごとの違いをまとめると？
- 段階: 基礎

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 下の層 | TCP | TCP | **UDP（QUIC）** |
| 1本の接続で並列処理 | できない（順番待ち） | できる（ストリーム） | できる（ストリーム） |
| HTTPレイヤーのHoL | **あり** | なし | なし |
| TCPレイヤーのHoL | あり | **あり** | なし |
| コネクション数 | 多い | 少ない | 少ない |

どのバージョンを使うかは、最近のブラウザは HTTP/3 まで対応しているので、**主にサーバ側の対応しだい**。
