# データセンター・仮想化

VXLAN・EVPN、サーバ仮想化、コンテナ。

## VXLAN

### VXLANは何をする技術？
- 段階: 基礎
- 出典: R6 午後Ⅱ 問1

**IP（レイヤー3）のネットワークの上に、離れた場所どうしをつなぐ「仮想のレイヤー2ネットワーク」を作る技術。**

- 元のイーサネットフレームを丸ごと IP/UDP の箱に入れて（カプセル化して）運ぶ。実際に運ぶ道（IPネットワーク）を **アンダーレイ**、その上の仮想L2を **オーバーレイ** という
- 箱に入れたり出したりする出入口の機器を **VTEP**。VTEP同士をつなぐ仮想の道が **VXLANトンネル**
- 仮想L2の区別には **VNI**（24ビット）を使う。2の24乗 ≒ **約1,677万個**。VLAN ID は12ビット（約4,000個）なので、データセンターで顧客（テナント）ごとにネットワークを分けるときもVLANより余裕がある
- L3ネットワークの上に作るので、経路が複数あっても全部使える（ECMP）。ネットワークを広げやすい

### VXLANパケットの構造は？ オーバーヘッドは何バイト？
- 段階: 知識
- 出典: R6 午後Ⅱ 問1 設問1

外側から順に、こう重なる。

| 順 | ヘッダー | 役割 |
|---|---|---|
| 1 | （外側のイーサネットヘッダー） | 次の機器へ運ぶ |
| 2 | **IPv4ヘッダー** | 送信元・宛先 ＝ VTEPのIPアドレス |
| 3 | **UDPヘッダー** | 宛先ポートは **UDP/4789** |
| 4 | **VXLANヘッダー** | **VNI（24ビット）** が入る |
| 5 | **イーサネットフレーム** | サーバが出した元のフレーム |

- 外側に足されるのは 14（イーサ）＋20（IPv4）＋8（UDP）＋8（VXLAN）＝ **50バイト**。元のフレームが1,500バイトの通信を通すには、途中の回線のMTUを大きくしておく必要がある
- UDPを使うのは、**送信元ポートをフローごとに変えて**、途中のECMPで負荷分散させやすくするため

### VLAN IDとVNIは、どう対応づける？ 違うVLAN IDでも通信できる？
- 段階: 知識
- 出典: R6 午後Ⅱ 問1 図4

VTEPの設定で「**VLAN ID ↔ VNI ↔ マルチキャストのグループアドレス**」の3つを1行ずつ対応させる。

- L2で通信できるかどうかは **VNIが同じかどうか** で決まる。VLAN IDやIPアドレスは関係ない
- VLAN IDは機器ごと（VTEPごと）に別の値でよい。**VNIが同じなら同じL2ネットワーク** につながる
- 同じVNIには同じグループアドレスを割り当てる

R6 午後Ⅱ 問1 の例：VLAN 110（L3SW11）・210（L3SW21）・310（L3SW31）は、どれも VNI 10010 ＝ 239.0.0.1。だから3つは1つのL2ネットワーク。

### VTEPは、宛先をどうやって覚える？ BUMフレームとは？
- 段階: 知識
- 出典: R6 午後Ⅱ 問1

**VXLANパケットを受信するたびに、「この MACアドレスは、このVNIの、このVTEPの先にいる」と記憶する。**（スイッチのMACアドレス学習と同じ考え方）

| 覚えるもの | どこから取る？ |
|---|---|
| サーバのMACアドレス | 中のイーサネットフレームの送信元MAC |
| VNI | VXLANヘッダー |
| リモートVTEPのIPアドレス | 外側のIPv4ヘッダーの送信元IP |

送るとき：
- 宛先MACが **覚えてある** → そのリモートVTEPのIPアドレス宛に **ユニキャスト** で送る
- 覚えていない、またはブロードキャストなど → **BUMフレーム**。宛先がわからないので、関係しそうな相手全員に送る

**BUM** ＝ **B**roadcast（例：ARP要求）、**U**nknown unicast（宛先MACを覚えていないユニキャスト）、**M**ulticast。

現行の方式（EVPNなし）は、BUMを **IPマルチキャスト** で全VTEPに届け、返事が来て初めて覚える。

### VXLANのネットワークで、ARPはどう運ばれる？
- 段階: 知識
- 出典: R6 午後Ⅱ 問1 設問3

サーバAがサーバBのMACアドレスを知りたいとき（現行のマルチキャスト方式）。

1. サーバA → 自分のVTEP：**ARP要求**（ブロードキャスト）
2. 送信側VTEP：BUMなので VXLANにカプセル化し、**そのVNIのマルチキャストグループアドレス宛** に送る。ここで **サーバAのMAC・VNI・自分のIP** を相手に覚えさせる
3. グループに参加している他のVTEP：カプセル化を解いて、対応するVLANに **ブロードキャスト**
4. サーバB：**ARP応答**（ユニキャスト）を返す
5. Bのいる側のVTEP：覚えてあるAのMAC → 送信元VTEPのIP宛に **ユニキャスト** で転送。ここで **サーバBのMAC・VNI・自分のIP** を覚えられる
6. 送信側VTEP：カプセル化を解いて、サーバAに応答を渡す

→ 往復が終わると、両方のVTEPが相手サーバのMACを覚えた状態になる。

### VXLANパケットのVNIは何ビット？ オーバーレイは何層のネットワークの上に作る？
- 段階: 過去問
- 出典: R6 午後Ⅱ 問1 設問1(1)a・b
- 本文: ◎

**a：24（ビット）、b：3（レイヤー3）**

VNIは24ビットなので、2の24乗 ≒ 約1,677万個。本文の「約1,677万個のレイヤー2のオーバーレイネットワーク」から逆算できる。VXLANは **レイヤー3（IP）のネットワークの上に** レイヤー2のオーバーレイを作る。

> 「約○万個」と書いてあれば、ビット数を逆算する。2の10乗＝1,024、2の20乗＝約104万、2の24乗＝約1,677万。

### VXLANパケットで、VXLANヘッダーの外側（IPv4ヘッダーの内側）に付くヘッダーは？
- 段階: 過去問
- 出典: R6 午後Ⅱ 問1 設問1(1)c
- 本文: ◎

**UDP**

VXLANパケットは、外側から IPv4ヘッダー → **UDPヘッダー** → VXLANヘッダー → イーサネットフレーム の順。UDPの宛先ポートは4789。

> 「トンネル（カプセル化）の中身の並び」→ 外側から、**IP → UDP → VXLAN → 元のフレーム**。

### VTEPが宛先を決めるために学習する3つの情報は、それぞれVXLANパケットのどこに入っている？
- 段階: 過去問
- 出典: R6 午後Ⅱ 問1 設問1(2)
- 本文: ○

- ① リモートVTEPに接続されたサーバのMACアドレス → **イーサネットフレーム**
- ② VXLANトンネルのVNI → **VXLANヘッダー**
- ③ リモートVTEPのIPアドレス → **IPv4ヘッダー**

VTEPは受信したVXLANパケットを、外から順に見る。
- 外側の **IPv4ヘッダーの送信元IP** ＝ 送ってきたVTEPのIPアドレス
- **VXLANヘッダー** ＝ VNI
- 中身の **イーサネットフレームの送信元MAC** ＝ そのVTEPの先にいるサーバのMAC

> 図2のようなパケット構造の図が出たら、「学習する情報」は **外側のIP（VTEP）・VXLANヘッダー（VNI）・中のフレーム（サーバ）** の3層に1つずつ対応する。

### BUMフレームの宛先IPアドレスを、IPマルチキャストのグループアドレスにして転送する目的は？
- 段階: 過去問
- 出典: R6 午後Ⅱ 問1 設問1(3)
- 本文: ◎

**同じレイヤー2のネットワークをもつ全てのリモートVTEPに転送するため。**

BUMフレームは、宛先がわからない（またはブロードキャスト）ので、同じL2ネットワーク（同じVNI）にいる全員に届ける必要がある。VNIごとにマルチキャストのグループを決めておき、そのVNIを持つVTEPだけがグループに参加する。送信側は **グループアドレス宛に1回送るだけ** で、ネットワークが参加者全員に届けてくれる。関係のないVNIのVTEPには届かない。

> 「なぜマルチキャスト？」→ **相手のVTEPが誰か知らなくても、同じL2（同じVNI）の全員に届けられるから**。

### VTEPのIPアドレスに、物理インタフェースではなくループバックインタフェースのIPアドレスを使うのはなぜ？
- 段階: 過去問
- 出典: R6 午後Ⅱ 問1 設問2(4)
- 本文: ◎

**一つの物理インタフェースに障害があってもVTEPとして動作できるから。**

物理インタフェースのIPアドレスだと、そのインタフェースが故障するとVTEPのアドレスごと使えなくなる。ループバックは **機器の中の仮想のインタフェース** で、物理の口に依存しない。L3SWは複数の経路（スパイン2台）でつながっているので、1本が切れても別の経路でそのアドレスに届く。

> 「ループバックのIPアドレスを使う理由」→ **物理インタフェースが故障してもアドレスが消えない（機器が生きていれば到達できる）**。ルータIDでも、VTEPでも、BGPピアリングでも同じ。

### あるVMとレイヤー2で通信できる相手のVMは、どう判断する？（VLAN 230につながるVMの場合）

| VM | VLAN ID | VNI |
|---|---|---|

### ARP応答をユニキャストで返すために、VTEPがARP要求を含むVXLANパケットから学習する情報は？

- 出典: R6 午後Ⅱ 問1 設問3(2)
- 本文: ○
- 状況: K社の検証ネットワークで、VM11（L3SW11側）が VM31（L3SW31側）のMACアドレスを問い合わせるARP要求を出した。VM31 はARP応答を返す。L3SW31のVTEPは、このARP応答を L3SW11のVTEPにユニキャストで転送する。

## データセンターのネットワーク構成

### スパイン・リーフ構成とは？
- 段階: 基礎
- 出典: R6 午後Ⅱ 問1 図3

データセンターの定番の形。**リーフ**（サーバをつなぐスイッチ）の全部を、**スパイン**（リーフ同士をつなぐスイッチ）の全部とつなぐ。

- リーフ ↔ リーフ の通信は、必ず **スパインを1台だけ経由** する（リーフ → スパイン → リーフ）
- どのリーフ間も同じホップ数・同じ距離になる
- スパインを増やせば帯域が増える。1台止まっても残りで通信できる
- スパインが複数あるので、**ECMP** で負荷分散する

R6 午後Ⅱ 問1 の図3：スパイン＝L3SW01・L3SW02、リーフ＝L3SW11・12・21・22・31・32。サーバはリーフ側につながる。

## EVPN

### EVPNは何をするもの？
- 段階: 基礎
- 出典: R6 午後Ⅱ 問1

**VXLANのオーバーレイネットワークを制御するための情報を、MP-BGPで配る仕組み。**（RFC 7432、RFC 8365）

| | 担当 |
|---|---|
| コントロールプレーン（情報を配って決める） | **EVPN（MP-BGP）** |
| データプレーン（フレームを実際に運ぶ） | **VXLAN** |

- EVPNなし：VTEPは受信したパケットから学習する（**後追いで覚える**）。わからなければ BUMフレームで全体に聞く
- EVPNあり：VTEPが **MP-BGPで「うちのサーバのMACはこれ」と事前に教え合う**

**MP-BGP** ＝ BGPを拡張して、IPv4経路以外（MACアドレスなど）も運べるようにしたもの。

### EVPNを使うと、VXLANの何が変わる？
- 段階: 知識
- 出典: R6 午後Ⅱ 問1

| 機能 | 現行（EVPNなし） | EVPNあり |
|---|---|---|
| 1：リモートVTEPの学習 | 受信したVXLANパケットから | MP-BGPで **事前に** 学習（リモートVTEPのIPアドレス、VNI など） |
| 2：サーバの情報の学習 | 受信したVXLANパケットから | MP-BGPで **事前に** 学習（サーバのMAC、VNI、リモートVTEPのIP） |
| 3：サーバとの接続 | 複数のVTEPとサーバの間で **リンクアグリゲーションを使えない** | **ESI** を交換して、複数のVTEPとサーバの間でリンクアグリゲーションを使える |

効果：
- 機能1 → BUMフレームを **IPユニキャストで** 運べる。IPマルチキャスト（PIM）が要らない
- 機能2 → 宛先MACを前もって知っているので、**Unknown Unicastのフラッディング** が減る
- 機能3 → 2本の回線を **両方** 使える

BUMの運び方：EVPNでは、VTEPが「このVNIを持つVTEPはどれか」の一覧（EVPNのルートタイプ3）を持つ。BUMフレームを受けたら、**そのVNIを持つ全てのリモートVTEP宛に、1台ずつユニキャストで複製して送る**。

### EVPNで、サーバのMACアドレスなどをMP-BGPで事前に学習できるようになると、BUMフレームのうち何によるフラッディングが減る？
- 段階: 過去問
- 出典: R6 午後Ⅱ 問1 設問4(2)f
- 本文: ◎

**Unknown Unicast**

機能2では、VTEPがMP-BGPで **サーバのMACアドレス、VNI、リモートVTEPのIPアドレスを事前に学習** する。宛先MACがわかっているので「宛先を知らないユニキャスト（Unknown Unicast）」が発生せず、全体に撒く（フラッディングする）必要が減る。ネットワークの負荷が下がる。

> EVPNの **事前学習** ＝ 宛先がわからないときの **Unknown Unicastのフラッディングが減る**。BroadcastやMulticastはなくならない（ARP要求は残る）。

### 同じ物理サーバにつながる2台のL3SWの、リンクアグリゲーションの論理インタフェースに同じに設定するものは？
- 段階: 過去問
- 出典: R6 午後Ⅱ 問1 設問4(2)g
- 本文: ◎
- 状況: K社の新検証ネットワークでは、1台の物理サーバの2つのNICを、2台のL3SW（L3SW11・L3SW12 など）にそれぞれつなぎ、リンクアグリゲーションで束ねる。

**ESI（Ethernet Segment Identifier）**

2台のL3SWが同じESIを持つと、MP-BGPでESIを交換して「この2台は同じサーバにつながっている」と認識する。これで、2台のスイッチにまたがったリンクアグリゲーションが使える。

### EVPNのESIを使って、サーバの2つのNICを2台のスイッチにリンクアグリゲーションでつなぐと、NICのアクティブ／スタンバイと比べて何が良い？
- 段階: 過去問
- 出典: R6 午後Ⅱ 問1 設問4(3)
- 本文: ○
- 状況: K社の現行の検証ネットワークでは、物理サーバの2つのNICをアクティブ／スタンバイにしている。新検証ネットワークでは、EVPNの機能3を使い、2つのNICをアクティブ／アクティブにして、2台のL3SWとリンクアグリゲーションで接続する。

**二つの回線の帯域を有効に利用できる。**

現行はアクティブ／スタンバイで、待機側の回線は普段使わない。新しい方は、両方の回線で同時に通信できる。（どちらかが切れても続けられる点は同じ）

> 「アクティブ／アクティブの利点」→ **待機していた回線も使えて、帯域を有効に使える**。

### EVPN構成で、あるVLAN IDのARP要求フレームは、どのリモートVTEPに転送される？（“VNI”を使って）

## VDI

### VDI（仮想デスクトップ基盤）とは？ なぜテレワークで使う？
- 段階: 基礎
- 出典: R4 午後Ⅱ 問1

**サーバの上に利用者ごとの仮想PC（仮想デスクトップ）を用意し、手元のPCからは画面だけを遠隔操作する** 仕組み。

- 業務データは **サーバ（データセンター）の中にだけ** あり、自宅の個人PCには残らない → 情報漏えいのリスクが小さい
- 個人PCには、画面を操作する **VDIクライアント** を入れる。画面の転送には **RDP** などを使う
- 仮想PCから業務サーバにアクセスするので、社内にいるときと同じ業務ができる

## 仮想化

### コンテナ仮想化とサーバ仮想化（ハイパーバイザ型）は何が違う？
- 段階: 基礎
- 出典: R4 午後Ⅱ 問2

| | サーバ仮想化（ハイパーバイザ型） | コンテナ仮想化 |
|---|---|---|
| 仕組み | 物理サーバ上の **ハイパーバイザ** が、仮想サーバ（仮想マシン）を動かす | **1つのOS** の上に、仮想的に分離したアプリの実行環境（コンテナ）を作る |
| ゲストOS | **仮想サーバごとに必要** | **要らない**（ホストのOSを共有） |
| 起動 | OS の起動が要るので遅い | **速い**（アプリだけ起動） |
| 資源の無駄 | CPU・メモリを多く使う | **少ない** |
| 向いているもの | OSごと分けたい、特殊なアプリ | 軽く、たくさん動かしたい（R4 午後Ⅱ 問2 では WebAP） |

R4 午後Ⅱ 問2 の方針：まずコンテナ化できるAPをコンテナにして、向かないAPは仮想サーバ（ハイパーバイザ型）にして、移行が終わったらAPサーバを廃止する。

### コンテナサーバの中のネットワークは、どうなっている？（仮想ブリッジ、仮想ルータ）
- 段階: 知識
- 出典: R4 午後Ⅱ 問2

R4 午後Ⅱ 問2 図3の構成：

- コンテナの **仮想NIC** → **仮想ブリッジ**（L2スイッチの役割）でつながる。この中のネットワークを **仮想ブリッジセグメント** という
- 仮想ブリッジと外のLAN（NIC経由でL2SW）の間に **仮想ルータ** がある
- 仮想ルータが **NAPT**（コンテナ → 外）と **ポートフォワード**（外 → コンテナ）を行う

つまり、コンテナはコンテナサーバの **中にある小さなプライベートネットワーク** にいて、外からは **コンテナサーバのIPアドレス** にしか見えない。自宅のルータの内側にあるPCと同じ関係。

### 物理サーバの上で、複数の仮想サーバを動かすためのソフトウェアを何という？
- 段階: 過去問
- 出典: R4 午後Ⅱ 問2 設問1(1)ア
- 本文: ◎

**ハイパーバイザ**。

ホストサーバ（物理サーバ）の上で動き、**1台の物理サーバに複数の仮想サーバを動かす** ソフトウェア。仮想SW（仮想L2スイッチ）や仮想NICも、ハイパーバイザが提供する。

### VRRPを組む2台のAP仮想サーバを、同じホストサーバに入れると、可用性の面でどんな問題がある？
- 段階: 過去問
- 出典: R4 午後Ⅱ 問2 設問1(2)
- 本文: ◎
- 状況: U社は、1つのAPを2台のAP仮想サーバで構成して、VRRPで冗長化する。AP仮想サーバは、ホストサーバ（物理サーバ）の上で動く。

**ホストサーバが停止した場合、AP仮想サーバが2台とも停止する。**

冗長化の目的は「1台が止まっても、もう1台で続けられる」こと。ところが、2台が同じ物理サーバの上にいると、その物理サーバが故障しただけで **両方いっぺんに止まり**、VRRPの切替えもできない。だから、**別々のホストサーバ** に入れる。

> 冗長構成の「同じ物の上に置くな」問題 →「**同じ機器・同じ電源・同じ回線** が止まると両方止まる」（単一障害点）と答える。

### 複数のコンテナサーバで、コンテナの仮想ブリッジセグメントに同じIPアドレスを使って問題ないのはなぜ？
- 段階: 過去問
- 出典: R4 午後Ⅱ 問2 設問2(1)
- 本文: ○
- 状況: U社のコンテナサーバaとbは、それぞれ仮想ブリッジセグメントを持ち、どちらにも同じネットワーク（172.16.0.0/24）を割り当てる。コンテナの仮想NICのIPアドレスは、このセグメントの中にある。コンテナが外のPCやDBサーバと通信するときは、コンテナサーバの仮想ルータを通る。

**外部ではコンテナサーバに付与したIPアドレスが利用されることはないから。**

コンテナのIPアドレス（172.16.0.x）は、コンテナサーバの **中だけ** で使われる。外から見えるのは、コンテナサーバのIPアドレス（192.168.0.112 など）だけ。

- コンテナ → 外：仮想ルータが **NAPT** で、送信元をコンテナサーバのIPアドレスに変換する
- 外 → コンテナ：仮想ルータが **ポートフォワード** で、コンテナのIPアドレスに転送する

家庭ごとに同じ 192.168.0.0/24 を使っても、ルータの外では混ざらないのと同じ。

### 仮想ルータがポートフォワードで変換した後の、宛先IPアドレスと宛先ポート番号は？
- 段階: 過去問
- 出典: R4 午後Ⅱ 問2 設問2(4)
- 本文: △
- 状況: 共用リバースプロキシが、192.168.0.112 の8000番宛てに通信を送る。192.168.0.112 はコンテナサーバaのIPアドレスで、その仮想ブリッジセグメントaの中に、WebAPコンテナ（AP0a）が 172.16.0.16/24、WebAPコンテナ（AP1a）が 172.16.0.17/24 で動いている。AP0の振り分け先は8000番、AP1は8001番。

**宛先IPアドレス 172.16.0.16、宛先ポート番号 80**。

仮想ルータのポートフォワードは「192.168.0.112:8000 → AP0a（172.16.0.16）:80」というルール。

図のつながり方（要点）：
- 共用リバースプロキシ（192.168.0.98）が送るパケット：宛先 192.168.0.112:**8000**
- 仮想ルータが書き換えた後：宛先 **172.16.0.16:80**（AP0a）。送信元は、192.168.0.98 のまま
- 同じように、8001番宛ては 172.16.0.17（AP1a）の80番へ

### 専用APをコンテナにするとき、仮想ルータの、どんな2つの機能が正しく動くか確認する必要がある？
- 段階: 過去問
- 出典: R4 午後Ⅱ 問2 設問3(1)
- 本文: ○
- 状況: U社の専用APは、TCP/IPを使った独自のプロトコルで、PCからアクセスされる。専用APをコンテナとして動かすとき、PCや共用DBサーバなど外部のホストとの通信は、コンテナサーバの仮想ルータを通る。

**NAPT機能** と **ポートフォワード機能**。

- コンテナ → 外（共用DBサーバなど）：仮想ルータの **NAPT** で送信元が変わる
- 外（PC）→ コンテナ：仮想ルータの **ポートフォワード** で宛先が変わる

独自プロトコルは、パケットの中にIPアドレスやポート番号を埋め込んでいたり、APからPCへ接続し返したりすることがある。そのときは NAT で書き換えると壊れる。HTTPのように決まった動きではないので、**APごとに動作確認が必要**。
