# 認証

RADIUS・IEEE 802.1X・Kerberos・SAML などの利用者認証と、メールの送信ドメイン認証。

## 送信ドメイン認証

### なりすましメールとは？ SPF・DKIM・DMARCは何をする？
- 段階: 基礎
- 出典: R6 午後Ⅱ 問2

SMTPには差出人を確かめる仕組みがなく、**送信元メールアドレスは誰でも好きに書ける**。そこで **受信側が、そのドメインの持ち主から本当に送られたか** を確かめる。これが **送信ドメイン認証**。

| | 何を確かめる？ | 何を使う？ |
|---|---|---|
| **SPF** | **送信元のメールサーバのIPアドレス** が、そのドメインの許可リストにあるか | DNSのTXTレコード |
| **DKIM** | メールに付いた **電子署名** が正しいか（改ざんも検知） | 署名はメールのヘッダー、公開鍵はDNS |
| **DMARC** | SPF・DKIMの結果が、見えている差出人（Fromヘッダー）と合っているか。失敗したときの扱いも決める | DNSのTXTレコード |

受信側は、失敗したメールを **隔離または廃棄** できる。

### SMTPの MAIL FROM とメールのFromヘッダーは何が違う？
- 段階: 知識
- 出典: R6 午後Ⅱ 問2 設問2(2)

SMTPは、封筒（エンベロープ）と便せん（ヘッダー・本文）を別々に扱う。

| | どこに書く？ | 何のため？ |
|---|---|---|
| **MAIL FROM**（エンベロープFrom） | SMTPコマンド | 配送が失敗したときの **返送先** |
| **RCPT TO** | SMTPコマンド | 配送先 |
| **From**（ヘッダーFrom） | メールのヘッダー | 受信者が **メールソフトで見る** 差出人 |

SMTPのやり取り：**EHLO（HELO）→ MAIL FROM → RCPT TO → DATA（ヘッダーと本文）→ QUIT**。

どちらも自分で好きに書けるので、**詐称できる**。SPFは主に **MAIL FROM** のドメインを検査する。

## SPF

### SPFレコードはどう書く？ どう検証する？
- 段階: 知識
- 出典: R6 午後Ⅱ 問2 設問2

SPFレコードは、**ドメインのDNSにTXTレコードとして** 登録する。

```
y-sha.com.  IN  TXT  "v=spf1 +ip4:200.a.b.1 +ip4:200.a.b.2 -all"
```

- `v=spf1`：SPFのバージョン
- `ip4:`：メール送信を許可するIPv4アドレス（範囲も書ける）。`+` は「許可」（省略可）
- `-all`：**それ以外は全部拒否**（`~all` なら、失敗扱いだが受け取る）

検証の流れ（受信側）：
1. SMTPの **MAIL FROM** のドメインを取り出す
2. そのドメインの **権威DNSサーバ** からSPFレコードを取得する
3. メールを送ってきた **メールサーバのIPアドレス** が、レコードに載っているか調べる

弱点：メールを **転送** すると、送信元IPが転送サーバに変わるので失敗する。また、見えている差出人（Fromヘッダー）ではなく **MAIL FROM** を検査する。

### SPFレコードに登録するIPアドレス（ウ・エ）は？
- 段階: 過去問
- 出典: R6 午後Ⅱ 問2 設問2(1)
- 本文: ○
- 状況: Y社のサポートメールは、社内メールサーバYからDMZのメール中継サーバY1・Y2を経由して、顧客のメールサーバに届く。外部DNSサーバYのSPFレコードに、正規の送信元として2つのIPアドレスを `+ip4:` で書き、最後に `-all` を付ける。

**ウ・エ：200.a.b.1 と 200.a.b.2**（順不同）

顧客のメールサーバから見て、メールを送ってくるのは **メール中継サーバY1・Y2**（グローバルIPは静的NATで 200.a.b.1、200.a.b.2）。内部の 192.168.0.x（プライベート）や、社内メールサーバ（y-mail3）ではない。

> SPFには **外から見える送信元のグローバルIP** を書く。送信が最後に出ていく機器のIP。

### SPFの流れで、顧客のメールサーバがMAIL FROMから入手するもの（d〜f）は？
- 段階: 過去問
- 出典: R6 午後Ⅱ 問2 設問2(2)
- 本文: ○
- 状況: 顧客のメールサーバは、メール中継サーバY1またはY2から、メール転送プロトコルで受け取ったコマンドの指定アドレスのドメイン名を入手し、そのドメインのゾーンを管理する外部DNSサーバYから SPF レコードを取得する。サポートメールの送信元メールアドレスは support@y-sha.com。

**d：SMTP、e：MAIL FROM、f：y-sha.com**

メール転送プロトコル（**SMTP**）の **MAIL FROM** コマンドで指定されたメールアドレス（support@y-sha.com）の、**ドメイン名（y-sha.com）** を取り出す。そのドメインのゾーンを管理する外部DNSサーバYから、SPFレコードを取得する。

> SPFが見るのは、**SMTPのMAIL FROMのドメイン**。

### SPFで、送信元のメールサーバの正当性はどう確認する？
- 段階: 過去問
- 出典: R6 午後Ⅱ 問2 設問2(3)
- 本文: ◎

**送信元のメールサーバのIPアドレスが、SPFレコードの中に登録されていること。**

顧客のメールサーバは、実際に接続してきたメール中継サーバのIPアドレスを、取得したSPFレコードの `ip4:` の一覧と照らし合わせる。載っていれば正当。載っていなければ（`-all`）なりすましと判断して、隔離または廃棄する。

> SPFの確認方法 → **接続してきた送信元IPが、SPFレコードに載っているか**。

### 委託先のメール中継サーバから送るメールにSPFを通すには、どのDNSサーバに何を登録する？
- 段階: 過去問
- 出典: R6 午後Ⅱ 問2 設問4(1)
- 本文: △
- 状況: Y社は、サポート業務をZ社に委託する。Z社の担当者は、送信元アドレスを support@y-sha.com にして、Z社のメール中継サーバZ（z-mail1）から顧客にサポートメールを送る。Y社の外部DNSサーバY（y-ns1）には、すでにY社のSPFレコードがある。z-mail1 のIPアドレスは 222.c.d.1。

**DNSサーバ名：外部DNSサーバY（y-ns1）。登録する情報：メール中継サーバZ（z-mail1）のIPアドレス。**

顧客のメールサーバは、MAIL FROM のドメイン（**y-sha.com**）のゾーンを管理するDNSサーバからSPFレコードを取る。つまり引き先は **Z社のDNSではなく、Y社の外部DNSサーバY**。そこのSPFレコードに、Z社のメール中継サーバのIPアドレス（`+ip4:222.c.d.1`）を **追加する**。

> 外部委託の問題で「SPFをどうする？」→ **送信元ドメイン（自社）のDNSに、委託先の送信サーバのIPを追加**。委託先のDNSに書いても意味がない。

### 委託先の他部署の従業員が問合せ窓口のアドレスになりすましても、顧客のメールサーバで検知できない理由は？
- 段階: 過去問
- 出典: R6 午後Ⅱ 問2 設問4(4)
- 本文: ○
- 状況: Z社のサポートチームY以外の部署の従業員が、送信元メールアドレスに support@y-sha.com を付けて、サポート担当者になりすます。Z社のメール中継サーバZは、送信元メールアドレスが support@y-sha.com のメールにDKIM処理をしていて、そのIPアドレスはY社のSPFレコードにも登録されている。

**なりすましメールも、メール中継サーバZから社外に転送されるから。**

Z社の従業員のメールは、部署に関係なく、すべて Z社のメール中継サーバZを通って社外に出る。中継サーバZは「送信元が support@y-sha.com」のメールには全部DKIM署名を付け、送信元IPもY社のSPFに登録済み。だから、なりすましメールも **SPFもDKIMも成功する**。顧客のメールサーバから見ると、正規のメールと区別がつかない。

SPF・DKIMが保証するのは **「このドメインのサーバから出た」** ところまで。**誰が書いたか（個人）** は保証しない。そこで、個人ごとに署名する **S/MIME** が有効になる。

> SPF・DKIMは **サーバ（ドメイン）単位** の認証。**人（個人）単位** のなりすましには、S/MIMEが必要。

## DKIM

### DKIMはどういう仕組み？
- 段階: 知識
- 出典: R6 午後Ⅱ 問2 設問3

**送信側のメールサーバが、メールに電子署名を付ける。受信側がDNSから公開鍵を取って、署名を検証する。**

1. 送信側：メールの **ヘッダーの一部と本文** からハッシュ値を作り、**秘密鍵で署名** する。結果を **DKIM-Signatureヘッダー** に入れて送る
2. 受信側：DKIM-Signatureヘッダーの **d（ドメイン名）と s（セレクター）** を見る
3. 受信側：DNSから `セレクター._domainkey.ドメイン` のTXTレコード（DKIMレコード）を引いて **公開鍵** を取る
4. 受信側：公開鍵で署名を検証する。合えば、**正規のメールサーバから送られ、改ざんされていない**

特徴：
- **認証局（CA）の証明書は要らない**。鍵はサイトの管理者が自分で作る
- 1つのドメインに **セレクターを複数** 置ける。セレクターごとに別の鍵を使える
- 転送されても、署名の対象部分が変わらなければ検証できる（SPFより転送に強い）

### DKIMレコードとDKIM-Signatureヘッダーのタグは？
- 段階: 知識
- 出典: R6 午後Ⅱ 問2 設問3(2)

**DKIMレコード**（DNSのTXT）：`sel.ysha._domainkey.y-sha.com.  IN TXT "v=DKIM1; k=rsa; t=s; p=..."`

| タグ | 意味 |
|---|---|
| v | バージョン（DKIM1） |
| k | 署名に使う鍵の形式（**rsa**） |
| t | フラグ。規格（RFC 6376）では **t=y がテスト中**、t=s は「署名ドメインのサブドメインを認めない」指定。試験の表では t=s を本番運用の意味で説明していた |
| **p** | **Base64でエンコードした公開鍵** |

**DKIM-Signatureヘッダー**（メールに付く）：

| タグ | 意味 |
|---|---|
| b | Base64でエンコードした **電子署名データ** |
| d | 署名を行った **ドメイン名** |
| s | DKIMレコードを引くときの **セレクター名** |

DKIMレコードの名前は、DKIM-Signatureの **s と d** から作る：`s._domainkey.d`。

### DKIMの電子署名のデータは、メールの何を基に生成される？
- 段階: 過去問
- 出典: R6 午後Ⅱ 問2 設問3(1)g
- 本文: ◎

**ヘッダー**（メールの「ヘッダー」及び本文を基に生成）

署名の対象は、ヘッダーの一部（From など、署名に含めると決めたもの）と本文。DKIM-Signatureヘッダーの中に、署名データ（b）が入る。

### DKIMレコードで指定されている暗号化方式のアルゴリズム名と、pタグに入れる鍵名は？
- 段階: 過去問
- 出典: R6 午後Ⅱ 問2 設問3(2)
- 本文: ○
- 状況: Y社の外部DNSサーバYには、sel.ysha._domainkey.y-sha.com というTXTレコードで、`v=DKIM1; k=rsa; t=s; p=（省略）` というDKIMレコードを登録している。表2では、pタグは「Base64でエンコードした［オ］のデータ」とされている。

**アルゴリズム名：RSA、オ：公開鍵**

`k=rsa` が署名に使う鍵の形式（RSA）。`p=` には、**署名の検証に使う公開鍵** をBase64で入れる。秘密鍵はメールを送るサーバだけが持ち、DNSには載せない。

### DKIMの電子署名の真正性を検査すると、送信者がなりすまされていないことがわかるのはなぜ？
- 段階: 過去問
- 出典: R6 午後Ⅱ 問2 設問3(3)
- 本文: ◎

**受信したメールが正規のメールサーバから送信されたものかどうかが分かるから。**

電子署名は、**秘密鍵を持つ正規のメールサーバにしか作れない**。受信側は、ドメインのDNSに公開されている **公開鍵** で署名を検証する。検証に成功すれば、そのドメインの正規のメールサーバが署名したメールだとわかる（ついでに、署名した範囲が改ざんされていないこともわかる）。

> 電子署名の検証が成功する ＝ **秘密鍵の持ち主（正規のサーバ）が作った** ことの証明。

### 委託先のメール中継サーバでDKIM署名するとき、dタグに登録するドメイン名は？
- 段階: 過去問
- 出典: R6 午後Ⅱ 問2 設問4(2)j
- 本文: ○
- 状況: Z社のメール中継サーバZが、送信元メールアドレスが support@y-sha.com のメールにDKIM署名する。顧客のメールサーバは、外部DNSサーバYを使ってDKIMの検査をする。セレクター名は sel.zsha を使う。

**y-sha.com**

DKIM-Signatureの **dタグ** ＝ 署名したドメイン名。顧客のメールサーバは `s._domainkey.d`（sel.zsha._domainkey.y-sha.com）を、**Y社の外部DNSサーバY** に引きにくる。だから d は **Y社のドメイン** にして、Y社のDNSにDKIMレコードを追加する。

> 委託先が署名するときも、d は **差出人のドメイン（自社）**。鍵だけ委託先のものを使う。

### DKIMのセレクターを分けて、委託先に異なる鍵を使わせる利点は？（委託元のセキュリティ面）
- 段階: 過去問
- 出典: R6 午後Ⅱ 問2 設問4(3)
- 本文: ◎
- 状況: Y社のメール中継サーバY1・Y2は、セレクター sel.ysha の鍵で署名している。Z社のメール中継サーバZは、セレクター sel.zsha の別の鍵で署名する。

**メール中継サーバZから鍵が漏えいしても、Y社で実施中のDKIMの処理は影響を受けない。**

Y社の鍵（sel.ysha）と、Z社の鍵（sel.zsha）が別なので、Z社から秘密鍵が漏れても、**sel.zsha のDKIMレコードを消すだけ** で済む。Y社が使っている鍵は変わらないので、Y社のメール中継サーバの設定を変える必要がない。

> 「別の鍵・別の担当を分ける」利点 → **片方が漏えい・障害になっても、もう片方に影響が及ばない**（被害の範囲を限定できる）。

## S/MIME

### S/MIMEとは？ DKIMとは何が違う？
- 段階: 基礎
- 出典: R6 午後Ⅱ 問2

**メールに電子署名を付ける（暗号化もできる）規格。送信者本人のMUA（メールソフト）が署名し、受信者のMUAが検証する。**

署名のしかた：
1. 送信者のMUAが、メール内容の **ハッシュ値** を作る
2. ハッシュ値を **送信者の秘密鍵で暗号化** して、電子署名データを作る
3. **電子証明書** と署名付きのメールを送る
4. 受信者のMUAが、電子署名データを **送信者の公開鍵（電子証明書）で復号** してハッシュ値を取り出し、自分で作ったハッシュ値と **比べる**。同じなら改ざんされていない

| | DKIM | S/MIME |
|---|---|---|
| 署名する人 | **メールサーバ**（ドメイン単位） | **利用者本人**（個人単位） |
| 鍵・証明書 | 自分で作った鍵（CA不要） | **CAが発行した電子証明書** が必要 |
| 検証する人 | 受信側のメールサーバ | 受信者のMUA |
| 防げるもの | ドメインのなりすまし | 個人のなりすまし・内容の改ざん |

R6 午後Ⅱ 問2 設問5 はこの署名の手順を問う設問だったが、IPAが「不備により設問が成立しない」と発表したので、解答例はない。

## 証明書

### 電子署名とは？ 署名と検証には、誰のどの鍵を使う？
- 段階: 基礎
- 出典: R4 午後Ⅱ 問1

**データに対して「確かに本人が作った／改ざんされていない」ことを示すしるし。**

- **署名**：署名する人が、自分の **秘密鍵** でデータ（のハッシュ値）を暗号化する
- **検証**：受け取った人が、署名した人の **公開鍵** で復号し、データのハッシュ値と一致するか調べる

秘密鍵は **本人しか持っていない**。だから、その公開鍵で検証できる署名は「本人が付けたもの」だとわかる。

覚え方：**暗号化は「相手の公開鍵で暗号化 → 相手の秘密鍵で復号」、署名は「自分の秘密鍵で署名 → 相手が自分の公開鍵で検証」**。

### クライアント証明書認証とは？ ID・パスワード認証より何が良い？
- 段階: 基礎
- 出典: R4 午後Ⅱ 問1

**利用者に配った証明書（と秘密鍵）で、本人であることを確かめる認証。** TLSのやり取りの中で行われる。

- サーバがクライアントに証明書の提示を求める
- クライアントは証明書を送り、**秘密鍵で署名** して「この秘密鍵を持っているのは私」と示す
- サーバは、証明書がCAに署名されたものか・失効していないかを検証し、**Subjectなどから誰かを特定** する

パスワードのように盗み見・使い回し・推測がしにくい。証明書ごとに失効もできる。

### サーバ証明書のコモン名とは？ ブラウザはTLSハンドシェイク中に何を確認する？
- 段階: 知識
- 出典: R5 午後Ⅱ 問2 設問2(1)

ブラウザは、サーバから受け取った **サーバ証明書** について、次を確認する。

1. 信頼できる認証局（CA）が署名していること
2. 有効期限内であること
3. 失効していないこと
4. **URLのホスト名が、証明書の中のサーバ名と一致すること**

**コモン名（CN）** ＝ 証明書に書かれたサーバ名（FQDN）。複数のドメインに対応するマルチドメイン証明書は、**サブジェクト代替名（SAN）** に複数のホスト名を登録する（最近のブラウザは SAN を見て照合する）。

どれかが合わないと、ブラウザが警告・エラーを出す（TLSハンドシェイクの中で判断する）。

### 電子証明書（X.509）には、どんな項目が書かれている？
- 段階: 知識
- 出典: R4 午後Ⅱ 問1

「この公開鍵は、この人（サーバ）のものです」と **CA（認証局）が保証** する書類。主な項目：

| 項目 | 中身 |
|---|---|
| **Subject**（サブジェクト） | 証明対象（誰の証明書か）。サーバならFQDN、人なら名前や利用者IDなど |
| Issuer | 発行したCA |
| 有効期間 | いつからいつまで |
| **公開鍵** | 証明対象の公開鍵（秘密鍵は本人だけが持つ） |
| **シリアル番号** | CAが発行した証明書ごとに付ける番号。そのCAの中で一意 |
| **CAのデジタル署名** | CAが、上の内容に対して署名したもの。改ざんされていない証拠 |

### 受け取った証明書が正しいかは、何を確認する？ なぜCAのルート証明書が要る？
- 段階: 知識
- 出典: R4 午後Ⅱ 問1

主な確認事項：

1. **CAの署名が正しいか**（CAの公開鍵で検証）。CAの公開鍵は **CAのルート証明書** に入っている
2. 有効期間内か
3. **失効していないか**（CRLやOCSPで確認）
4. 証明書の Subject が、接続しようとしている相手（FQDNなど）と一致しているか

ルート証明書は **信頼の出発点** なので、あらかじめ検証する側の機器にインストールしておく。入っていない（信頼できない）CAが発行した証明書は、検証に失敗する。

### CSR（証明書署名要求）とは？
- 段階: 知識
- 出典: R4 午後Ⅱ 問1

**CAに証明書を発行してもらうための申請データ。**

1. 申請者が **公開鍵と秘密鍵のペア** を作る（秘密鍵は自分で持ち続ける）
2. 公開鍵と、Subject などの情報をまとめて **CSR** を作り、**自分の秘密鍵で署名** する
3. CSR をCAに送る。CAは申請者本人かなどを確認し、**CSRの署名を検証** して、証明書を発行する

秘密鍵はCAに渡さない。CSRの署名は「この公開鍵に対応する秘密鍵を、申請者が持っている」ことの証明になる。

### CRL（証明書失効リスト）とは？ 何が載っている？
- 段階: 知識
- 出典: R4 午後Ⅱ 問1

**有効期間内でも、使ってはいけなくなった証明書の一覧。** CAが発行する。

- 失効した理由：秘密鍵の漏えい、社員の退職、紛失など
- 載っているのは **失効した日時** と、その証明書を一意に識別する **シリアル番号**
- 証明書を検証する側は、CRLを取得して、相手の証明書が載っていないかを確認する

CRLを使わず、問い合わせ形式で失効を確認する方法は **OCSP**。

### サーバ証明書のコモン名が原因で、社内用のURLだとブラウザにエラーが出るのはなぜ？
- 段階: 過去問
- 出典: R5 午後Ⅱ 問2 設問2(1)
- 本文: ○
- 状況: Y社のECサイトには、会員企業が https://ecsv.example.jp/ でアクセスする。運用担当者は、運用PCから社内用の https://ecsv.y-sha.example.lan/ でアクセスすると、TLSのハンドシェイク中にブラウザにエラーが出る。ECサーバに登録されているサーバ証明書は1つで、マルチドメインには対応していない。

**コモン名とURLのドメインとが異なるから**

ブラウザは、URLのホスト名（ecsv.y-sha.example.lan）が、証明書のコモン名（ecsv.example.jp）と一致するかを確認する。証明書は1つで、マルチドメイン対応ではないので、**どちらか一方のドメインにしか一致しない**。社内用のURLでは不一致になり、エラーになる。

> 「証明書でエラーが出る」→ **URLのホスト名と証明書のコモン名（SAN）が合っているか** を確認する。

### 電子証明書に含まれている、証明対象の（ ）鍵は何鍵？

**公開**（鍵）。

### 電子証明書で、証明対象を識別する情報を入れるフィールドの名前は？

誰（どのサーバ・どの利用者）の証明書かを示す欄。サーバ証明書ならFQDN、クライアント証明書なら利用者の名前や、R4 午後Ⅱ 問1 のように **社員番号（利用者ID）** などを入れる。

### クライアント証明書で、送信元の身元を一意に特定できるのはなぜ？
- 段階: 過去問
- 出典: R4 午後Ⅱ 問1 設問3(1)

**クライアント証明書の公開鍵に対する秘密鍵は本人しか保有していないから。**

TLSのやり取りでクライアントは、証明書と、**秘密鍵で作った署名**（CertificateVerify）を送る。装置が証明書の公開鍵でその署名を検証できれば、「この証明書に対応する秘密鍵を持つ人」だとわかる。その秘密鍵は本人しか持たないので、送信元が一意に特定できる。

> 「証明書で身元が特定できる理由」→ **秘密鍵は本人だけが持っている**、と答える。

### クライアント証明書を検証するために、あらかじめSSL-VPN装置にインストールしておくものは？

**CAのルート証明書**。

### SSL-VPNクライアントがSSL-VPN装置から送られたサーバ証明書を検証すると、減らせるリスクは？
- 段階: 過去問
- 出典: R4 午後Ⅱ 問1 設問3(3)
- 本文: ◎

**なりすまされたSSL-VPN装置へ接続してしまうリスク。**

サーバ証明書は「この装置は確かに本物」というCAの保証。検証していないと、攻撃者が用意した偽の装置に接続して、クライアント証明書やその後の通信を渡してしまうおそれがある。

> 「サーバ証明書の検証で防げること」→ **偽のサーバへの接続（なりすまし）**。「クライアント証明書の検証」は逆に、**偽の利用者の接続**。

### 利用者がCSRに署名するときに使う鍵と、CAがCSRの署名を検証するときに使う鍵は？
- 段階: 過去問
- 出典: R4 午後Ⅱ 問1 設問3(5)
- 本文: ○
- 状況: K社の利用者は、自分で公開鍵と秘密鍵を作り、公開鍵から証明書署名要求（CSR）を作って、CAサービスに提出する。CAサービスは、K社の管理者への確認と、CSRの署名の検証を行ってから、クライアント証明書を発行する。

- 署名に用いる鍵：**利用者の秘密鍵**
- 署名の検証に用いる鍵：**利用者の公開鍵**

「署名は自分の秘密鍵で、検証は相手（署名者）の公開鍵で」の基本どおり。CSRには利用者の公開鍵が入っているので、CAはそれを取り出して検証できる。これで「この公開鍵に対応する秘密鍵を、申請者が確かに持っている」ことが確かめられる。

> 署名の問題 → 「**署名は署名者の秘密鍵、検証は署名者の公開鍵**」。CAの署名なら CA の鍵、利用者の署名なら利用者の鍵。誰が署名したかで鍵が決まる。

**シリアル番号**。

CRLには、失効した証明書の「シリアル番号」と「失効した日時」が並ぶ。シリアル番号は、そのCAが発行する証明書ごとに付ける一意の番号。

## SAML

### SAMLとは？ SP・IdP・SAMLアサーションとは？
- 段階: 基礎
- 出典: R5 午後Ⅱ 問2 設問6

**SAML** ＝ 認証・認可の情報を、**組織やサービスをまたいで** やり取りするための標準規格。一度の認証で複数のサービスを使える **SSO（シングルサインオン）** を実現できる。

| 登場人物 | 役割 | R5 午後Ⅱ 問2 |
|---|---|---|
| **IdP**（Identity Provider） | 利用者を認証し、**SAMLアサーション**（認証・認可の情報のXML文書。デジタル署名付き）を作る | 会員企業が用意（認証連携サーバ） |
| **SP**（Service Provider） | IdPのアサーションをもとに、利用者にサービスを提供する | Y社のECサーバ |
| 利用者 | ブラウザで両者の間を行き来する（リダイレクト） | 購買担当者 |

メリット：Y社は、会員企業の従業員のアカウントを **自分で管理しなくてよくなる**（会員企業側のIdPが認証する）。

### SAMLアサーションの3つの種類は？
- 段階: 知識
- 出典: R5 午後Ⅱ 問2 設問6

| 種類 | 書かれている内容 |
|---|---|
| **認証アサーション** | 利用者がIdPに **いつ・どこで・どの認証方式で** ログインしたか |
| **属性アサーション** | 利用者の **名前・生年月日・所属** など、利用者を識別・説明する情報 |
| **認可決定アサーション** | その利用者に、**サービスを利用する権限があるか** などの情報 |

SPは、アサーションを受け取ると「正当な利用者であることの確認」と「提供するサービス範囲（利用権限）の付与」の2つを行う。

### SAMLでSSOするときの流れ（SP起点）は？
- 段階: 知識
- 出典: R5 午後Ⅱ 問2 設問6

1. 利用者が **SPにアクセス** してログインを要求する
2. SPは **SAML Request** を作り、ブラウザを **IdPへリダイレクト**（転送）させる
3. IdPが **利用者を認証** する（R5 では、社内のケルベロス認証と連携）
4. IdPは **デジタル署名付きのSAMLアサーションを含む SAML Response** を作り、ブラウザを **SPへリダイレクト** させる
5. SPは **デジタル署名を検証** し、問題なければ利用者にサービスを提供する

ポイント：SPとIdPは、直接通信せず、**ブラウザ（利用者）を介して** メッセージをやり取りする。事前に **信頼関係**（SPがIdPの公開鍵証明書を登録しておく）を築いておく。

### SAMLで、ログイン要求を受けたECサーバがIdPへリダイレクトするために必要な情報は？
- 段階: 過去問
- 出典: R5 午後Ⅱ 問2 設問6(1)
- 本文: ○
- 状況: Y社のECサーバがSAMLのSPになる。購買担当者がログインを要求すると、ECサーバはSAML認証要求（SAML Request）を作って、利用者の認証・認可の情報を提供するIdPへリダイレクトさせる。IdPは会員企業ごとに別々のものがある。

**アクセス元の購買担当者が所属している会員企業の情報**

IdPは **会員企業ごとに違う**。ECサーバは、**どの会員企業の担当者か** が分からないと、**どのIdPへ転送すればよいか** を決められない。

> 「SPが必要とする情報」→ **IdPが複数あるなら、どのIdPかを決める情報（所属組織）**。

### SAMLの通信手順で、ECサーバに登録しておくべき情報は？
- 段階: 過去問
- 出典: R5 午後Ⅱ 問2 設問6(2)
- 本文: ◎
- 状況: SAMLを利用するために、Y社のECサーバ（SP）には、IdPが作成するデジタル署名の検証に必要な情報などを設定しておき、IdPとの間で信頼関係を築いておく。

**IdPの公開鍵証明書**

IdPは、SAMLアサーションに **自分の秘密鍵でデジタル署名** を付ける。SPは、その署名を **IdPの公開鍵で検証** する。公開鍵が本物であることを確かめるために、**IdPの公開鍵証明書** をSPに登録しておく。

### SPがSAMLアサーションに対して、デジタル署名の検証で確認できる内容を二つ挙げると？
- 段階: 過去問
- 出典: R5 午後Ⅱ 問2 設問6(4)
- 本文: ◎

**① 信頼関係のある IdP が生成したものであること**
**② SAML アサーションが改ざんされていないこと**

デジタル署名の検証でわかるのは、**「誰が作ったか」と「改ざんされていないか」** の2つ。SPは、事前に登録したIdPの公開鍵証明書で検証するので、**信頼関係のあるIdPが作ったもの** だとわかる。

> 「デジタル署名で確認できること」→ **作成者の正当性** と **改ざんの有無**。

## ケルベロス認証

### ケルベロス認証の登場人物（KDC・TGT・ST）は？
- 段階: 基礎
- 出典: R4 午後Ⅰ 問3

- **KDC**（鍵配布センタ）：PCとサーバの鍵を管理し、チケットを発行する。DS（ディレクトリサーバ）のアカウント情報をもとに認証する
- **TGT**：利用者の **身分証明書** にあたるチケット。ID・パスワードで認証されると発行される
- **ST**：その利用者が、**特定のサーバの認証を受けるためのチケット**。TGTを見せてKDCにもらう

特徴：
- 共通鍵暗号で認証・暗号化する。パスワードそのものはネットワークに流れない
- チケットには **有効期限** がある。PCとサーバの時計がずれていると、期限の判断を間違える
- 全てのPC・サーバの鍵を、KDCにも事前に登録しておく

### ケルベロス認証でWebサーバにアクセスするまでの流れは？（PC起動〜ST提示）
- 段階: 知識
- 出典: R4 午後Ⅰ 問3 設問2

| 番号 | 誰と誰 | やりとり | ポート |
|---|---|---|---|
| ①② | PC ⇔ KDC | ID・パスワードで認証要求 → **TGT** を受け取る（PCの鍵で暗号化されている） | **88** |
| ③④ | PC ⇔ サーバ | HTTP要求 → サーバが「ケルベロス認証で来て」（401 ＋ WWW-Authenticate: Negotiate） | HTTP/HTTPS |
| ⑤⑥ | PC ⇔ KDC | TGTを見せて、このサーバ用の **ST** を要求 → ST（サーバの鍵で暗号化）を含む情報が、PCの鍵で暗号化されて返る | **88** |
| ⑦⑧ | PC ⇔ サーバ | STをサーバに提示 → サーバがSTの中身でPCを認証し、アクセス権限を付与 | HTTP/HTTPS |

**サーバがKDCに問い合わせなくていい**のは、STがサーバの鍵で暗号化されていて、サーバ自身が中身を確かめられるから。

### KDCが発行したSTを、PCが改ざんできないのはなぜ？
- 段階: 過去問
- 出典: R5 午後Ⅱ 問2 設問6(3)
- 本文: ○
- 状況: 会員企業e社のPCは、ケルベロス認証でKDCからSTの発行を受ける。KDCは、購買担当者の身元情報とセッション鍵を含むSTを、IdP（認証連携サーバ）の鍵で暗号化してから、PCに渡す。PCはSTを取り出して、IdPに提示する。

**IdPの鍵を所有していないから**

STは **提示先（IdP）の鍵で暗号化** されている。PCはその鍵を持たないので、中身を読むことも、書き換えたうえで **正しく暗号化し直す** こともできない。改ざんしても、IdPが復号できずに失敗する。

> 「〇〇が改ざんできない理由」→ **暗号化・署名に使った鍵を持っていないから** と答える。

### 攻撃者が、PCがKDCから受け取る認証成功の応答（TGTの払出し）を盗聴しても、営業支援サーバを使えないのはなぜ？（15字以内）
- 段階: 過去問
- 出典: R4 午後Ⅰ 問3 設問2(1)
- 本文: ○
- 状況: Y社のSSOでは、PCがKDCにID・パスワードを送って認証を受け（図2の①）、KDCがTGTをPCの鍵で暗号化して返す（②）。PCはTGTを見せて営業支援サーバ用のSTを要求し（⑤）、KDCは、STを含む情報をPCの鍵で暗号化して払い出す（⑥）。PCは、その中からSTを取り出して営業支援サーバに提示する（⑦）。

**STを取り出せないから**

攻撃者が②を盗聴してTGTを手に入れても、それだけでは使えない。

- ⑥でKDCが返す、STを含む情報は **PCの鍵で暗号化** されている（実際のケルベロスでは、②でPCだけに渡されるセッション鍵で暗号化される）
- 攻撃者はその鍵を持たないので、盗んだTGTでSTを要求しても、返ってきた情報を復号できず、⑦で営業支援サーバに見せる **ST を取り出せない**

> 「盗聴されても大丈夫な理由」→ **暗号化されていて、鍵を持たない人は中身を使えない**。

### ケルベロス認証のポート番号88が使われる通信は、図2の①〜⑧のどれ？
- 段階: 過去問
- 出典: R4 午後Ⅰ 問3 設問2(2)
- 本文: △
- 状況: Y社のSSOの通信手順（図2）：①PC→KDC 認証要求（ID・パスワード）、②KDC→PC 認証成功（TGT）、③PC→営業支援サーバ HTTP要求、④営業支援サーバ→PC HTTP応答（401、WWW-Authenticate: Negotiate）、⑤PC→KDC 営業支援サーバ用のST要求（TGT）、⑥KDC→PC STの払出し、⑦PC→営業支援サーバ HTTP要求（ST提示）、⑧営業支援サーバ→PC HTTP応答（200 OK）。

**①、②、⑤、⑥**

88番はKDC（ケルベロス認証サービス）が待ち受けるポート。**PCとKDC（DS）の間** の通信（①②⑤⑥）が対象。③④⑦⑧は、PCと営業支援サーバの間のHTTP（S）の通信なので、88番ではない。

> 「どの通信か」→ 図2の矢印の **両端が誰か** を見る。KDCとの通信なら88番。

### ケルベロス認証で、PCとサーバの間で有効期限が正しく判断できない問題を発生させないための対策は？（20字以内）
- 段階: 過去問
- 出典: R4 午後Ⅰ 問3 設問2(3)
- 本文: ◎
- 状況: Y社のSSOで使うTGTとSTには有効期限が設定されている。PCとサーバの間で有効期限が正しく判断できないと、有効期限内でも、PCが提示したSTをサーバが使用不可と判断する可能性がある。

**PCとサーバ間で時刻同期を行う。**

有効期限は「今の時刻」と比べて判断する。PCとサーバの時計がずれていると、期限内のSTでも「期限切れ」「まだ有効でない」と判断されてしまう。**NTP** で時刻を合わせる。一般にケルベロス認証では、時計のずれの許容は数分以内（5分程度が標準）。

> 「ケルベロス認証が失敗する」→ まず **時刻のずれ** を疑う。

## 認証と認可

### 認証と認可の違いは？
- 段階: 基礎

| | 認証 | 認可 |
|---|---|---|
| 確かめること | **この人は本人か** | **この人にこの操作をする権限があるか** |
| 手段の例 | ID・パスワード、証明書 | アクセス権の設定、ロール（役割） |
| 順番 | 先 | 認証のあと |

例：FTAにログインできる（認証）ことと、承認ボタンを押せるのは指定された上長だけ（認可）ことは別の話。

### FTAで、認証と認可はそれぞれ何をするために使われる？（各25字以内）
- 段階: 過去問
- 出典: R4 午後Ⅰ 問1 設問2(3)
- 本文: ◎
- 状況: FTAは、既存のサーバにある認証・認可に必要な情報を参照して、利用者がファイルをアップロード・承認・ダウンロードできるかどうかを判断する。

- 認証：**FTAの利用者が本人であることを確認するため**
- 認可：**操作ごとに実行権限を有するかを確認するため**

例：ID・パスワードでログインさせるのが認証。ログインできた人でも、承認ができるのは設定された上長だけ、ダウンロードできるのは受信者に指定された人だけ、と **操作ごとに許す・許さないを決める** のが認可。

> 「認証と認可の違いを書く」→ 認証は **本人か**、認可は **その操作をしてよいか**。

## LDAP

### LDAPサーバ（ディレクトリサーバ）とは？ 何のために使う？
- 段階: 基礎

利用者の **ID・パスワード・メールアドレス・所属などのアカウント情報を、1か所にまとめて管理するデータベース** にアクセスするためのプロトコルが LDAP（Lightweight Directory Access Protocol）。この情報を持つサーバをディレクトリサーバ（DS）という。

- メールサーバ・プロキシ・FTAなど、複数のシステムが同じLDAPサーバを見に行けば、**アカウントの管理が1か所で済む**（アカウントの一元管理）
- ポート：**TCP/389**（暗号化したLDAPSは TCP/636）
- Windows の Active Directory もディレクトリサーバの一種

### FTAの利用者認証を、既存のサーバで一元的に管理するなら、どのサーバから認証情報を取得する？
- 段階: 過去問
- 出典: R4 午後Ⅰ 問1 設問2(1)
- 本文: ○
- 状況: A社は、工場の管理セグメントと事務所のOAセグメントの間でファイルを受け渡すため、ファイル転送アプライアンス（FTA）を導入する。事務所には、社員のメールボックスをもつ内部メールサーバと、ユーザ認証のためにLDAPサーバを参照するプロキシサーバがある。

**LDAPサーバ**

本文に「内部メールサーバとプロキシサーバが、ユーザ認証のためにLDAPサーバを参照する」とある。**社員のアカウント情報はすでにLDAPサーバにある** ので、FTAもそれを参照させれば、FTA専用にID・パスワードを作らずに済む（アカウント情報の一元管理）。

> 「既存のサーバで一元管理」→ **本文で他の機器が認証のために参照しているサーバ** を探す。

## HTTPの認証方式

### プロキシの利用者認証で、ID・パスワードをBase64にするだけの方式（Basic）に対し、MD5やSHA-256でハッシュ化する方式は？
- 段階: 過去問
- 出典: R4 午後Ⅰ 問1 設問1(1)b
- 本文: ◎
- 状況: A社のプロキシサーバは、利用者の認証のために LDAPサーバを参照する。認証方式には、Base64でエンコードするBasic認証と、MD5やSHA-256でハッシュ化する認証があり、A社では後者を採用している。

**ダイジェスト**（認証）

| | Basic認証 | ダイジェスト認証 |
|---|---|---|
| 送るもの | ID:パスワード を **Base64にしただけ** | サーバが出した乱数などと、パスワードを **ハッシュ化した値** |
| 盗聴されると | Base64は暗号化ではなく **誰でも元に戻せる** → パスワードが丸見え | ハッシュ値からパスワードそのものはわからない |
| 注意 | TLSで保護しないと危険 | 総当たりなどの攻撃には注意が必要 |

> 「Base64でエンコード」は Basic、「ハッシュ化（MD5など）」は **ダイジェスト**。

## SSO

### SSO（シングルサインオン）とは？ 何が良い？
- 段階: 基礎
- 出典: R4 午後Ⅰ 問3

**一度認証すれば、複数のシステムに、改めてID・パスワードを入力せずに使える仕組み。**

- 利用者：パスワードの使い回しが不要になる → **パスワードリスト攻撃**（漏れたID・パスワードを他のサイトで試す攻撃）のリスクが減る
- 管理者：アカウント情報を一元管理でき、サーバごとの管理作業が減る

実現方式の例：**ケルベロス認証**（社内LAN向け。共通鍵暗号）、**SAML**（クラウドサービスとの連携）。
